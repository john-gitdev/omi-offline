# Changelog

Patch releases are rolled up into their minor version. Each section reflects the **net** behavior at the end of that series, so superseded or reverted intermediate changes aren't listed.

## App

### 0.34

- **Fix: long-pressing a recording no longer scrolls it away from you.** Long-pressing a recording or a ghost row starts a selection on that day, and starting one hides everything that is not that day — the other days' cards, the Unorganized section, and the marker rows under each recording. All of that sits above the row you pressed, so the row jumped up the page the instant the selection opened, often out of view entirely, and jumped back down when you left the selection. The list now scrolls itself so the row you pressed stays where it already was on screen, both when the selection opens and when it closes.

- **Change: the Manual mode icon no longer looks like a Stop sign.** The mode indicator in the top bar showed a raised open palm for Manual — an icon whose own description reads "halt, stop" — which suggested the app was refusing something rather than telling you which mode you are in. It is now a pointing hand, matching the icon already used for Button Configuration and reading as "you start and stop this yourself". Automatic keeps its wand. Nothing about the modes themselves changed.

- **Fix: the diagnostic log was destroying about a quarter of its own records.** Every line the app writes to the debug log is written without waiting for the one before it to land, and the log is appended to from several places at once. Each of those writes worked out where the end of the file was when it *started* writing, so two lines begun at the same moment both wrote to the same spot and the second landed on top of the first. The result was a log with lines spliced into the middle of other lines, and — worse, because it leaves no trace — whole entries simply gone. A log captured during a connection problem on 17 August had lost 141 of its 547 lines this way, which is exactly the kind of thing that makes a fault impossible to diagnose after the fact. Writes are now queued so each one finishes before the next begins. This also closes a rarer version of the same fault: the log is trimmed once it passes 20 MB by rewriting the file, which could previously happen underneath a write already in progress.

- **Improved: the connection-problem report is more useful.** Three changes, all to the diagnostics the app records when it repeatedly fails to reach your Omi. When it listens for your Omi to check whether it is still on the air, it now records how long it actually listened rather than how long it meant to — those differ, sometimes by a factor of two, because the app is usually backgrounded at the time, and the difference made the reading uncomparable between one report and the next. It now also remembers an unresolved connection problem across an app restart, so restarting or updating the app mid-problem no longer erases the record of it just before it gets resolved — which is precisely when the record is worth having, since restarting is what people try. And a problem resolved this way is marked as such, so its duration is read correctly.

- **Fix: the sync estimate could be wrong for a whole session.** The app asks your Omi once per connection which audio format it records in, and if that one question went unanswered it assumed the oldest format and never asked again for the rest of the session. Nothing was recorded or played back wrongly — the format only feeds the estimate of how many segments a sync will take — but the estimate could be off by roughly double. An unanswered question is now retried rather than treated as an answer.

- **Fix: shared debug logs kept their placeholder name on some destinations.** Sharing a log to Google Drive produced a properly descriptive name, but saving the same log to internal storage wrote `omi_debug_current.log` — the working name the app uses on disk. Only Drive and mail apps ever saw the good name, because those take it from the share sheet's title; a save-to-storage destination reads the file's own name instead, and that had never been changed. The log is now copied under its full name before being handed over, so every destination gets the same thing. The firmware version in that name also used to read `unknown` whenever the app hadn't connected to the Omi yet since launching — it now falls back to the firmware last seen on the paired device, which is the one that produced the log. And the leading `android_` is gone: this app is Android-only, so it distinguished nothing. Names now read `0.34.8_oo-3.0.6_omi_offline_debug_20260817.log`.

- **New: recordings say which mode they were made in.** The label on a recording used to read `VAD` or `AAD`, which named the speech detector rather than the mode — and it ran three different situations together, since Manual mode, Automatic with Silero switched off, and Automatic where the Silero model failed to load all showed the same `AAD`. Recordings now read **Manual**, **Auto/VAD** or **Auto/AAD**. Manual drops the detector half because it carries no information: Manual mode always has the detector off, so the recording is `AAD` by definition. On an Automatic recording it stays, where it genuinely distinguishes Silero from the plain loudness gate. The mode is recorded with the recording, so a backlog synced days later is labelled with the mode it was actually captured in rather than whichever mode you happen to be in now. Older recordings keep their existing label unless they were made with Silero — that alone proves they were Automatic, so those are relabelled `Auto/VAD` immediately; the rest are genuinely ambiguous and are left as `AAD` rather than guessed at. Turn the whole thing off under Settings → App Settings → **Show Recording Mode** to go back to the plain `VAD`/`AAD` labels; it is a display setting only and changes nothing on disk.

- **Fix: Device Settings and Button Actions came up with options missing.** Customization would show nothing but Button Configuration — no LED brightness, no LEDs On, no Connected LED, no mic gain — and Button Actions would quietly drop the Toggle action and the "Single recording button" switch. Nothing was wrong with the Omi. The app asks it once, on opening the page, which features it has, and that question travels the same channel as syncing and file listing; when it went unanswered the app took "no answer" to mean "your Omi doesn't have these" and hid the rows, with no message to say otherwise. Device Settings was in fact competing with **itself** — it asked that question at the same moment it asked how much space was free, and the space lookup holds the channel for several seconds. Button Actions had it worse: it is normally opened right after a mode switch, which is exactly when a sync is running. The app now asks once, when your Omi connects, in the quiet moment before syncing starts, and remembers the answer for both pages.

- **Change: Device Settings opens straight away.** Because the values are already known by the time you get there, the page no longer sits on a spinner while it interrogates the Omi — it comes up filled in, and quietly refreshes in the background. **Storage Free Space** may appear a beat after the rest; it is the one figure that still has to be fetched on the spot, and the rest of the page no longer waits for it.

- **Fix: a setting that never reached your Omi is no longer remembered as though it had.** Writing a setting reports no error even when it doesn't land, so the app now reads each one back after writing it. A confirmed value is remembered; anything else is discarded so the next visit asks the Omi rather than trusting a guess. The row keeps showing what you picked either way — a slider jumping back under your finger would be worse — but the app no longer claims a value it couldn't verify.

- **Fix: changing one setting no longer freezes the others.** If a setting was still being fetched when you changed a different one, the fetch was thrown away for **every** row, not just the one you touched — so the rest of the page could sit on stale values for as long as it stayed open, and write those values back. Each row is now tracked on its own.

- **Fix: pressing Stop left the recording stuck as "Conversation in progress" for hours.** (Firmware `oo-3.0.6`.) The Omi always has one file open that it is writing audio into, and it doesn't offer that file to the phone — only files it has finished with. Finishing one is called rotating, and the Omi decides whether to rotate *while it is saving audio*. Press Stop and the microphone parks, so no more audio is saved, so that decision never gets made again: the last stretch of the recording — including the "recording ends here" mark that tells the app to close it — sat on the Omi, invisible to every automatic sync. On the reported device that was 2.1 MB stranded for 2 hours 33 minutes across five background syncs, each told there was nothing to fetch; it only came back when Force Sync was pressed by hand, which sends an explicit rotate. Stopping a manual recording now finishes its file immediately, the same way stopping a Priority Recording always has, so the very next sync collects it. As a backstop the Omi also finishes an old file when your phone connects — previously it only intended to, and the intention was never acted on unless audio happened to be recording at the time. That backstop covers Automatic mode too, where a recording ends because the room went quiet and there is no Stop to hang anything off.

- **Fix: a stop signal arriving in its own batch no longer goes unused.** Rare, but permanent when it happened: if the "recording ends here" mark reached the phone in a later batch than the audio it closes, the app had nothing in hand to finalize and discarded it, leaving the recording parked under the banner. In manual mode nothing else can ever close a recording, so it stayed there until processed by hand. The mark is now applied to the parked recording it belongs to.

- **Fix: a new install recorded in Manual mode but cut the audio by Automatic's rules.** The app keeps which mode you are in separately from the handful of values that decide where recordings get cut, and on a brand-new install those two disagreed. A freshly flashed Omi starts in Manual, and so does the app — but the cutting values started at Automatic's: listen for speech, end a recording after two minutes of quiet, throw away anything with under three seconds of speech, and stop after an hour no matter what. So on a new phone, before you had ever opened Recording Settings, a recording you started with the button could be cut in half at a quiet patch, have its quiet stretches filed away as discarded, and stop dead after an hour. Nothing corrected it on its own — the app only reconciles the two when the mode actually changes, and on a new install it never had. The values are now brought into line with the mode every time the app starts, so a new install behaves as Manual from the first recording. Nothing changes for anyone who has already saved their recording settings.

- **Fix: Device Settings no longer comes up half empty while your Omi is syncing.** The page asks the Omi a dozen separate questions — brightness, mic gain, sensitivity, free space, firmware version — and each one can go unanswered even though the connection is fine, because a sync is using the same channel. The first question is which features the Omi has, and an unanswered one came back as "none", which is indistinguishable from an Omi that genuinely lacks them: five rows disappeared at once with nothing to say why. It now recognises a busy Omi, says **Waiting for sync to complete**, and fills the page in as soon as the sync ends. It also connects when you open it, rather than giving up if the app happened not to be connected already — the same fix as Button Actions above.

- **Fix: a long recording made by hand no longer comes back as two recordings.** When a sync ends partway through a recording the app parks what it has and joins it to whatever arrives next time. Deciding whether to join was a matter of how much quiet sat between the two — and in manual mode that amount is set to nothing, because manual recordings are ended by the button rather than by silence. Nothing was read as "any gap at all is a break", so the parked recording was closed off before the next batch could be joined to it. Any manual recording long enough to span two syncs was split in half, and had been for as long as manual mode has existed. It is now left open for the Omi's own stop signal to close, which is what ends a manual recording in the first place.

- **Fix: changing recording mode now takes effect, or tells you it didn't.** Switching modes writes the new mode to the Omi, and every layer beneath that write failed quietly — if the Omi had wandered out of range, or simply didn't answer, the app carried on as though it had. It then believed one thing while the Omi did another, and since the app takes the Omi's word for it on the next connection, the mode would quietly snap back while the rules that decide how your audio is cut stayed where the failed switch had left them. That is the same mismatch that caused the shredding above, arrived at from the other direction. The app now reads the setting back off the Omi to confirm it landed, and changes nothing at all if it didn't — you stay on the settings screen with your changes intact and a note asking you to try again.

- **New: a note when your Omi's recording mode isn't the one you picked.** Only one thing can change which mode an Omi is in, and that is you, from the app, while connected — so the two normally agree, and this stays out of your way. Pair a replacement Omi, though, and it arrives with its own idea of the mode. The app follows the device, as it always has, but now brings the rest of your recording settings along with it rather than leaving them behind pointing at the mode you were in before — and says so, with a note on the recordings screen offering to take you to Recording Settings. Your automatic-mode settings are kept whichever mode you end up in, so switching back restores exactly what you had. Nothing appears if you have never chosen a mode yourself: a fresh install has a default, not a preference.

- **Fix: Button Actions no longer says your Omi is missing when it is sitting right there.** Opening the screen asked whether the app happened to be connected already, and gave up if it wasn't — without trying to connect, and without saying so. Everything on the page was greyed out. It now connects, the way Find Devices and the firmware updater always have, showing its usual brief loading state while it does. This was most obvious straight after changing recording mode, since that is where the app offers to show you the screen.

- **Fix: switching recording mode no longer re-cuts the audio that is still waiting to be processed.** How a recording gets divided up is decided when the audio is processed, not when it is captured — and the two can be hours apart, because the Omi records whether or not your phone is nearby. Switching mode changed the rules immediately, so whatever was still waiting got divided by the rules of the mode you had just left it for. Both directions were wrong in their own way: audio recorded automatically, processed under manual rules, was cut apart at every file boundary and every time the Omi had woken from silence, turning one conversation into many; audio you had deliberately recorded by hand, processed under automatic rules, was passed through the speech filter that automatic mode uses to throw away noise, and a quiet recording could be discarded as though you had never made it. The rules are now attached to the audio rather than to the switch: each stretch is processed the way it was recorded, and only what the Omi captures after your most recent switch uses the current mode. Switching again before the older audio has been dealt with is fine — every stretch keeps its own rules. This needs nothing from you and nothing waits; the older audio is simply processed first, in its own pass. Audio still sitting on the Omi when you switch is covered too, whenever it eventually arrives, and so is audio still downloading at that moment.

- **Fix: switching to manual mode no longer shreds the waiting audio into thousands of twenty-millisecond recordings.** Automatic mode ends a recording after a set period of quiet, and that period is one of its settings. Manual mode has no use for it — a manual recording ends when you tap Stop — so saving the settings screen in manual mode set it to nothing. The check that ends a recording asked whether the quiet so far had reached the setting, and with the setting at nothing the answer was yes on every single frame of audio, quiet or not. Every twentieth of a second of unprocessed backlog was therefore closed and filed as its own recording: on 14 August, an hour and a half of waiting audio became seven thousand 684-byte files, each shown as lasting zero seconds, which took the app three minutes to write, wedged the processing pipeline, and left the recordings page unusable. Manual mode now leaves the recording open for the Omi's own stop marker to close, as it was always meant to. The setting still does its other job in manual mode — separating recordings across a gap between files, in case a stop marker is ever lost. Files already created this way are not repaired; delete that day's batch.

- **Fix: a Priority Recording no longer depends on when the Omi next reaches your phone.** The app has to remember between syncs that a Priority Recording is still running, because the tap that starts one and the tap that stops it can be hours apart and usually arrive in different batches. That memory carried an expiry, so that a stop instruction lost on the way could never leave the app recording everything indefinitely — but the expiry was counted in real time, by your phone's clock, at a bit over the Omi's own limit. The Omi records perfectly well for days without seeing your phone, so a long enough gap in syncing expired a recording that was in fact fine, and the remainder was then treated as ordinary audio: cut at silences with the quiet parts discarded. The limit is now counted in the recording itself. A Priority Recording runs until you stop it, or until it has captured as much audio as the Omi's safety cap allows — at which point it is cut into its own file and everything after it is ordinary audio again, which is exactly what the Omi itself did. When it syncs no longer comes into it. Because that limit now decides where a recording is cut rather than merely capping how long the app will keep believing in one, the app also keeps its own copy of the Omi's safety cap in step with the device. Opening Device Settings had been showing you the Omi's value without storing it, so a phone that had never set the cap itself went on assuming the default while the Omi held something else entirely — harmless while the number was only a ceiling, and not harmless once it is where the cut lands.

- **Fix: a Priority Recording no longer swallows the audio either side of it and overruns its own limit.** Starting one is meant to close whatever the Omi was already recording and begin a fresh recording at that moment; stopping it is meant to end that recording there. Both were done correctly while the audio was being decoded — but only within a single pass. A recording still in progress when a sync ends is held open and joined to the audio that arrives on the next sync, and that joining step went purely on timing: audio that carries on with no gap gets joined. The audio either side of a start or stop marker carries on with no gap by definition, so the recording that was in progress when you tapped Record Start was joined onto the front of the Priority Recording, and whatever followed the stop was joined onto the back. With a two-hour safety cap that the Omi honoured to the millisecond, one such recording arrived as two hours and eighteen minutes — fifteen minutes of conversation from before the tap, three from after the stop, and the red Priority Recording playing all of it. Both boundaries are now marked on the recording as it is written, and the joining step closes the earlier recording at the boundary instead of reaching across it. Recordings already on the phone are not re-cut.

- **New (dev): the debug log now records the app and firmware versions, so a change in either can be spotted in the log itself.** The log is the record you send when something has gone wrong, and the first question about anything odd in it is which versions produced it — which the log never said. It now stamps the app version every time the app opens, and the firmware version every time the Omi connects, along with whether the Omi has restarted since the last connection. A version that has changed since the last stamp is marked as such, so an update is a line you can find rather than something to reconstruct from memory. The restart is recorded separately and on purpose: a firmware update always ends in one, but it does not always change the version — reinstalling the same version can leave the version string untouched — and most restarts are not updates at all, so the reason for the last one is recorded next to it. Nothing is written when debug logging is off.

- **Change (dev): the shared debug log is named when you share it, not when it starts.** The file was named on the day logging was switched on and kept that name for its whole life, so a log collected over a fortnight arrived stamped with the date it began — which reads as the date of the contents and isn't. It now carries a placeholder name on the phone and is given its `<platform>_<app version>_<firmware>_omi_offline_debug_<date>.log` name at the moment you share it, so the date and the versions are the ones in force when you handed it over. The firmware part of that name is also right for the first time: it had been read from a copy of the device record that never carries the firmware revision, so every shared log — and the diagnostics snapshot you copy to the clipboard — called the firmware `unknown` whether the Omi was connected or not. The naming is otherwise unchanged, and nothing about what is logged or how long it is kept changes.

### 0.33

- **Change: Device Settings now shows a brief "Loading…" instead of assembling itself in front of you.** Everything on that screen — the brightness, mic gain and sensitivity values, the firmware version, the free space and file count — has to be asked of the Omi over Bluetooth, one question at a time, and each answer used to be added to the page the moment it arrived. So the page grew for about a second after opening, with rows appearing and pushing the ones below them down, which is exactly when you are reaching for something to tap. It now waits for the answers and shows the settings, device and hardware sections together. Reboot Omi and Shutdown Omi wait with them — both talk to the Omi over the same channel the questions are using, and there is no point offering them before the page can say whether the Omi is answering at all. Unpair Device stays available throughout, since it is the way out of an Omi that never finishes answering. Nothing extra is asked of the Omi and it takes no longer than before; if the Omi stops answering, the page gives up after fifteen seconds and shows whatever it did get, as it would have before.

- **Fix: a recording deleted from the Omi can no longer come back after a restart and be filed a second time.** Once the app has safely stored a recording it tells the Omi to delete its copy, and the Omi updates the index of what the card holds. If that index update was accepted but then failed to reach the memory chip, the deletion existed only in the Omi's memory — so restarting it before the next routine save brought the recording back, and the phone dutifully downloaded and processed it again as a duplicate. The Omi now re-attempts the index write at the moment it confirms the deletion, which is the last point it can still be retried on demand; if that fails too, the deletion is left to the next routine save and written to the log rather than reported as done. Requires firmware oo-3.0.3.

- **Fix: the first things the app asks the Omi for after reconnecting are no longer silently dropped.** Requests go to the Omi one at a time through a queue. When a connection ended, that queue was emptied in several separate steps, and a request arriving in the middle of them could either be thrown away or left sitting there with nothing to ever start it. A leftover request from the dead connection could also come back and cancel out one belonging to the new connection. Either way the first thing asked for after reconnecting — reading the battery, listing what is on the card, starting a sync — could quietly do nothing at all until some later action happened to nudge the queue back into motion. Clearing the queue is now a single indivisible step.

- **New (dev): the debug log now says when a request to the Omi hangs, and whether it ever came back.** The app gives up on a request after 10 seconds, but that give-up is one-sided — the Bluetooth layer underneath is never told. So in the log a request that was genuinely stuck, blocking everything queued behind it until the connection dropped, looked identical to one that was merely slow and completed a moment later, and those two want opposite fixes. Each request now names itself and is reported as `stalled` once it passes 10 seconds, then as `recovered` or `abandoned` depending on how it ended. A healthy connection writes nothing, and nothing is written at all when debug logging is off.

- **Fix: a sync that stalls partway is now retried in seconds instead of dropping the connection.** When the Omi went quiet in the middle of sending a recording, the app had no working way to notice. It was meant to give up after 15 seconds of silence and simply ask for that file again over the connection it already had. But the app also sends the Omi a heartbeat every 10 seconds so it doesn't hang up on an idle connection, and the Omi's reply to each heartbeat looked — to the part of the app listening for silence — exactly like the recording data it was waiting for. The silence was therefore never noticed, and a stalled transfer sat untouched for a full minute until a last-resort safety net stepped in and tore down the Bluetooth connection to clear the jam. That is why a stall showed up as the Omi disconnecting and the sync stopping partway, with the same recordings left to fetch again on the next attempt. Now only actual recording data counts as the Omi still being there, so a stall is caught in 15 seconds and the file is retried on a connection that stays up. The heartbeat also stands down completely while a transfer is running, since the Omi already knows not to hang up during one. This does not change how often a transfer stalls in the first place — it changes what a stall costs you.

- **Fix: the pairing request that pops up the moment a firmware update finishes no longer fails.** An update clears the Bluetooth pairing on both sides so the two can start fresh, but they don't clear it at the same instant: the phone clears its half as soon as the update lands, while the Omi clears its half when it finishes restarting a few seconds later. The app was reconnecting inside that gap — and an Omi that still holds the old pairing cannot accept a new one, so the request appeared and then failed, sometimes repeatedly. The app now waits until it can actually hear the Omi advertising again before reconnecting, which is the point at which the restart is genuinely finished. The pairing request still comes to you; accepting it now works first time. If the Omi takes unusually long to come back, tap Done and pick it from the device list as before.

- **Change: after a firmware update, you are no longer sent to the device list once the Omi has already reconnected.** The pairing request arrives on its own, so it can be accepted at any point — while the "Firmware updated" screen is still up, or after tapping Done. Whichever way round it happens, the app now stops asking you to do what is already done: accept it before tapping Done and the screen says so and Done goes straight back to your recordings; tap Done first and the device list closes itself the moment the Omi is back. Nothing on the device list is usable while an Omi is connected, so there was never anything to do there but leave.

- **New: the device list marks which Omi is yours.** Omis in range are told apart only by an address nobody has memorised. A green check now marks the one that is connected, and a grey check the one this phone is paired to but not currently connected — which is the one you are looking for whenever a paired Omi has stopped connecting, since that is exactly the case where nothing else on the row tells you apart. Unpaired devices are unmarked, as before. Note that an Omi you have just updated is unmarked too: the update clears the pairing on purpose, so there is nothing yet to mark until you have paired again.

- **Fix (dev): "empty bin rotations" no longer reports lost recordings that were never recorded, and now says what caused each one.** The Omi counts every time it closes a storage file that ended up holding no audio, and Diagnostics treated any of them as a possible lost recording. None of them are. A file can only close empty if *nothing at all* reached the memory card for it — not one moment of audio, not one bookmark — and a bookmark is written to the card the instant it happens, so it cannot be the missing piece. What is left is a file that was opened while nothing was being recorded, which in Automatic Mode is any quiet stretch: a Force Sync, a recording start or stop, or a clock sync opens a file, nobody speaks, and whatever rotates next closes it with nothing in it. Two Force Syncs across a quiet afternoon were enough to raise the alarm. Empty files are now reported plainly rather than as a fault, the warning is left to the counter that does mean lost audio, and the Omi records *why* each rotation happened so the event log names the cause — "app rotate command", "bin age", "priority recording stop" — instead of leaving you to guess. Requires firmware `oo-3.0.2` for the cause; older firmware says "unattributed" rather than guessing.

- **Fix: a recording the Omi refuses to delete is no longer downloaded and saved a second time.** After a recording transfers, the app tells the Omi to delete its copy. That instruction can come back refused — the Omi's storage was busy and didn't answer in time, most often. The app then had no memory that it already held the recording: the next sync saw the file still listed, downloaded it again, and — because the first copy had already been decoded and its working file cleaned up — saved the same audio a second time. The app now remembers which files it has in full, skips them, and retries only the deletion, which the Omi accepts the second time round. Two related effects of the same gap: a file that wouldn't delete stayed on the Omi indefinitely, since nothing ever asked again, and every sync reported itself incomplete because of it. The app also no longer carries on downloading past a recording it couldn't remove — it can only ever ask the Omi for the oldest file, so the one it couldn't delete is still the one it would be handed, and that file's audio would have been filed under the next recording's name and time.

- **Change: what Marker does is now stated on the button screen, per mode.** In Manual Mode it works while a recording is running — bookmarking a moment inside a long capture — and does nothing in standby, where there is no recording to bookmark. In Automatic Mode nothing changes, but the screen now tells you the part that was never stated anywhere: a marker doesn't only bookmark, it records for at least a minute from the tap and carries on recording if it hears anything — even if the Omi had decided the room was quiet, which is the whole point, since you can't know what it decided.

- **Change: the Omi's radio now idles between transfers instead of running flat out.** While connected, the link ran at the speed a file transfer needs — the radio waking about ninety times a second — for the entire time it was up, including the long stretches when nothing was being sent. It now runs at that speed only while a recording is actually transferring and drops to a far slower rate the rest of the time, which is most of it. Transfers are unaffected.

- **Fix: after a firmware update, reconnecting no longer takes several failed attempts.** An update deliberately clears the Bluetooth pairing on both sides, and the Omi was hanging up on the phone partway through establishing the new one — repeatedly, because each attempt was cut off at the same point. It now waits for pairing to finish. The Omi also waits a full minute before hanging up on a quiet phone rather than fifteen seconds, which was tight enough that ordinary operations kept getting caught by it.

- **Fix: opening the app during a connection outage now retries immediately instead of doing nothing.** When the Omi failed to connect, the app backed off before trying again — up to half a minute between attempts — and any request made during that wait was discarded, including opening the app yourself. So the one thing you'd naturally do when the Omi wasn't connecting was the one thing that couldn't help. Opening the app, and each scheduled sync, now interrupt the wait and try straight away. Repeated failures still slow down between attempts, which is what keeps a stuck connection from draining the battery.

- **Fix: a connection that succeeded could be reported as a failure.** The app gave up waiting sooner than the Bluetooth layer underneath it did, so a device that connected a few seconds late was recorded as a timeout and the working connection was thrown away — the sync then waited for the next scheduled window. The app now waits for the real answer.

- **New (dev): connection-outage records now show Bluetooth headsets, car kits and glasses, not just watches.** When the app fails to reach the Omi it writes a snapshot of what else the phone's Bluetooth radio was doing, and that snapshot only ever listed Bluetooth Low Energy links — so a car stereo, a headset or a pair of smart glasses, which connect a different way, was missing from every record. Those are the likelier culprits: audio links reserve slots on the radio that a connection attempt then has to fit around. Outage records now name the connected audio devices, and say whether audio was actually playing through them — an idle headset and a call in progress take very different amounts of the radio. A suspicion that "it can't connect after my car did" can now be checked against the log instead of guessed at.

- **Fix (dev): Debug Tools said diagnostics capture was on when the Omi's log was switched off.** The "capture" reading showed the app's own preference rather than the state of the device, and the two come apart: the command that arms the log is skipped whenever a sync is holding the storage connection, and the Omi clears it on every restart. So a snapshot could report capture on while the device was recording nothing, which makes an empty log look like a device with nothing to report. It now shows the device's confirmed state, the preference alongside it, and how long ago the two were last reconciled.
- **New (dev): Diagnostics reports microphone liveness and how much of the day is being recorded.** Two new readings from the Omi: how long since it last processed audio — a direct answer to "is the microphone working right now", instead of inferring it from a log that is also empty when the microphone is deliberately off — and total recorded time as a share of uptime. Requires firmware `oo-2.10.0`.

### 0.32

- **Change: the device list now only ever shows Omis found since you opened it.** It had been seeded with whatever the last scan turned up, however long ago that was, so the page could open showing an Omi that had since restarted, moved out of range or been switched off — a row that looks perfectly normal and can only fail when you tap it. It now starts empty and scans, every time it's opened and every time you refresh.
- **Change: after a firmware update the app takes you straight to pairing.** Every successful update clears the Bluetooth pairing on both sides (see below), so needing to pair again isn't a mishap — it's what happens every time. The finish screen said otherwise: it offered a cautiously-worded "Trouble reconnecting after the update?" note, and Done dropped you on the home screen next to an Omi that could no longer connect. It now states plainly that you need to pair again, walks through it, and Done opens the device list. The list is also emptied the moment the update lands: the Omi restarts right then, so anything found before it is a device that has already gone or is seconds from dropping, and tapping one of those entries could only fail.
- **Fix: reinstalling the same firmware version no longer looks like the update stalled partway.** An Omi update carries two images, one per processor core, and any image identical to what the device is already running is skipped rather than sent again — so reinstalling the same version transfers only the smaller of the two. The progress ring was still measuring against both, and so climbed to 41 %, sat there for the rest of the update, and jumped straight to "Firmware updated!". Every one of those updates had completed correctly; only the ring was wrong. A skipped image now counts as what it is — already installed — so the ring fills the whole way, and the part label names the image actually being written: a reinstall reads "Part 2 of 2", because the one that was skipped is the first.
- **Fix: a firmware update now always ends with a clean Bluetooth pairing.** Flashing the Omi rewrites the region of its memory that the pairing keys live next to, and occasionally a key didn't survive it. When that happened the result was the worst kind of failure: the Omi would connect, stay up for a second or two, then drop — over and over, forever. Nothing on the phone could fix it, because the Omi still held a pairing slot and refuses to accept a new pairing while one is occupied, whether the key in it still works or not. The only way out was an obscure five-tap-and-hold gesture on the device itself. Rather than hope the keys survive, both sides now simply clear the pairing after every successful update and pair again fresh, which takes no action from you. This happens on **every** update, including reinstalling the same version — which is exactly what someone does when pairing has already broken, so it's the last case that should be skipped. An update that fails or is cancelled part-way leaves your pairing completely untouched.

- **Fix: Device Settings no longer invents a firmware version when it doesn't know one.** Until the Omi's firmware revision has actually been read — before it connects, or if that read fails — the Firmware row had been falling back to `oo-1.0.9`, a real-looking version number belonging to no device in particular. It now reads `unknown`, matching what the Diagnostics snapshot already reported in the same situation.
- **Fix: a firmware update no longer looks like it installs the firmware twice.** An Omi update carries two images — one per processor core — and the progress ring counted each of them separately: it filled to 100 %, snapped back to 0 and counted up again, all under the same "Installing firmware…" heading, which read as the update restarting itself. Both passes were always part of one normal update, but nothing on screen said so. The percentage is now a single count across the whole update, with a "Part 1 of 2" line naming the image being written, so the ring only fills once. The "Firmware updated!" card at the end is also drawn full width, matching the card beneath it instead of sitting narrower than it.
- **Fix: Diagnostics reported a healthy Omi's lifetime Bluetooth tally as a current fault.** Nearly every reading in the panel counts from the last restart, but two — "Connect failures" and "Died at establishment" — are kept in the Omi's own flash and carry over every reboot, so they total the whole life of the device. Nothing said so. A used Omi therefore sat permanently on a red "2 issues — 19 BLE connect failures", where 19 meant "nineteen since you unboxed it", not "nineteen today". A link occasionally dying as it comes up is an ordinary radio event — the Omi has a Wi-Fi chip on the same board competing for the same airspace — so a handful accumulates on any device that works perfectly. Both rows are now labelled **(lifetime)** until you tap Mark baseline, and only count against the panel's verdict once a baseline makes them a genuine "since when" figure. What made these worth watching was always the number *moving*, never the number itself. The copied snapshot marks them the same way, since it sits under a "device up 5h 35m" heading that implied otherwise.
- **Change: Diagnostics no longer flags a slow SD operation that couldn't have cost anything.** The "slowest SD op since boot" reading warned above 500 ms, which sounds slow but isn't: a single operation writes 4 KB, and the queue behind it holds roughly twelve seconds of audio, so an operation has to be several times that long before it can drop so much as one block. Because the reading is a since-boot *maximum* that never decays, one harmless outlier hours into a run latched the warning on until the Omi restarted — amber on a panel where nothing had actually gone wrong. The warning now starts at 1000 ms, just below the point at which a single flush could genuinely exhaust the queue. Lost audio was, and still is, reported by the block-drop and NAND-error rows; this row only says which operation was responsible.
- **Fix (dev): the SD worker's stack bar in Diagnostics was drawn against the wrong size.** Dev builds carve the event log's 2 KB out of that thread's stack, leaving 10 KB where production has 12 KB — but the bar was measured against 12 KB either way. So the fill always read lower than it was, and worse, the "getting full" warning sat at a level *above the entire stack*, meaning it could not have fired however close the thread came to overflowing. The bar now follows the size the connected firmware was actually built with. Production builds were always shown correctly, and no reading was ever wrong on the device itself — only the scale the app drew it against.
- **Change: Debug Tools is reorganised, and its Diagnostics panel now tells you what it thinks.** The panel was a flat list of twenty-odd counters that, on a healthy device, read `0` almost the whole way down — so answering "is anything wrong?" meant scanning every row and knowing what each one meant. It now leads with a verdict: a green "All clear", or an amber/red headline naming what actually moved ("2 issues — 3 block drops · 1 marker write drop"), with device uptime alongside. The readings underneath are grouped (SD write path, recording markers, memory, BLE link) and each group folds itself away to a one-line summary while it's clean, expanding on its own the moment something in it moves — so a healthy panel is a handful of lines rather than a wall of zeroes. Colour now means one thing: amber is "worth a look", red is a fault, green is clear. Previously amber was also the page's accent colour, used for headings and ordinary buttons, and a single "any drops at all" flag painted several unrelated rows amber together — so a codec drop made the (zero) block-drop row look like a problem too. Stack and queue-depth readings are drawn as bars instead of "10.2 / 12.0 KB" text, and the panel no longer jumps down the page when the first reading arrives.
- **New: Debug Tools shows whether its diagnostics are actually live, and can copy a snapshot.** The panel had no way to say that its numbers had stopped updating — if the connection went quiet it simply kept showing the last values it received, indefinitely. A badge now reports whether readings are arriving live, coming from the slower fallback path, or have gone stale (and how long ago). A **Copy snapshot** button puts the whole set — counters, stacks, BLE failures and the captured event log, with app and firmware versions — on the clipboard as plain text, so reporting a problem no longer means screenshotting twenty rows.
- **Change: "Zero all counters" is now "Mark baseline", and is no longer a one-way door.** Zeroing the counters never touched the device — it recorded a baseline the app subtracts from, and the button's name said otherwise. Worse, there was no way back: the baseline was saved per-device and re-applied every time you reopened the page, so short of restarting the Omi — which drops the baseline, because its counters reset anyway — the device's real running totals were out of reach. A **Since baseline / Lifetime** switch now flips between the two views without discarding anything.
- **Change: the developer event log now lives inside the Diagnostics panel instead of a card of its own.** The counters total the same health events the event log timestamps, so they were only ever useful read together — they are now one panel, with the events as a group alongside the counter groups. Its capture control sits directly beneath the Diagnostics switch as a second switch of its own, rather than riding it: turning on the counters is a purely local thing that cannot fail, while starting event capture is a request to the Omi that can be refused while a sync is running and that the device forgets when it restarts. Keeping them separate means neither switch ever claims something about the device that isn't true. **Mark baseline** and **Copy snapshot** sit immediately under the pair, since both act on everything below them, and are greyed out until a reading has actually arrived rather than doing nothing when tapped. The event log also gains filter chips for the subsystem you're testing (Storage / Markers / BLE / Mic), a severity dot per entry, and a wall-clock time beside the device uptime so entries can be lined up against the app's own saved logs.
- **Change: Debug Tools' switches are grouped at the bottom of the page, with the actions above them.** Companion Device Pairing, Keep Screen On and Adjustment Mode were interleaved with the readouts and the delete buttons, which put a screen-wakelock toggle in the same visual rhythm as "permanently delete everything". The page now reads top to bottom as diagnostics, then actions, then options. **Save Debug Logs to File** is the deliberate exception and sits directly beneath the Diagnostics panel: the app's own log is read alongside the device's counters and event log when chasing a fault, and it was the one switch you had to scroll past every delete button to reach.
- **Removed: the Switch-backend control in Debug Tools.** The LittleFS storage backend is being retired, so the control that reformats the card between the two backends is gone. The Diagnostics panel still reports which backend the device mounted, and the ring backend's two SD-health readings — the slowest disk operation since boot, and NAND write errors — are now shown there for the first time (the app had been collecting both and only writing them to the log file).
- **Fix: the first launch after installing an app update no longer comes up half-connected (Android).** After installing a new APK the app could show the Omi as connected while being unable to do anything with it — no recordings would sync, and Device Settings → Customization showed only "Button Configuration", with LED brightness, mic gain, AAD sensitivity and the rest missing as though the firmware didn't support them. Force-closing the app and reopening it fixed it every time. Installing an update kills the app but leaves the background Bluetooth part to come back on its own, so the two can race: the link is established a moment before the phone has finished asking the Omi what it can do, and the app was being handed that empty answer as if it were final. It then had no way to reach anything on the device — every setting read came back blank (hence the collapsed Customization list) and every sync command failed — and, believing it was already connected, never tried again. The app now refuses an empty answer and waits for the real one, so the first launch after an update connects properly. Nothing was ever lost while this was happening; the recordings sat on the Omi and synced on the next working connection.
- **Fix: starting a sync and then leaving the app no longer cuts it short.** Tapping Sync only kept the *screen* awake — and that stops meaning anything the moment you switch apps or the screen locks, at which point nothing was keeping the phone's processor awake at all. The processor would sleep, the signal that stops the Omi hanging up on an idle connection stopped being sent, and the Omi dropped the connection about 15 seconds later, leaving the transfer half-finished. That's the everyday "started a sync, put the phone in my pocket, came back to a partial sync" case. The sync now holds the processor awake for as long as it's actually running, so backgrounding it — or locking the screen — no longer interrupts it.
- **Fix: very long background syncs no longer stop halfway.** Separately, the automatic background sync did hold the processor awake, but with a hard 30-minute expiry that was never renewed — and a large backlog (the Bluetooth transfer plus decoding the audio afterwards) routinely runs longer than that. Once it expired the same thing happened: the phone slept, and the Omi hung up. It's now renewed for as long as the work is actually running, with a ceiling so a stuck sync can't hold the phone awake indefinitely. Nothing was ever lost in either case — a partial sync resumes where it left off — but draining a backlog could take several attempts instead of one.

### 0.31

- **Fix: a shutdown that didn't complete could leave the Omi awake but permanently deaf.** Turning the Omi off — by the 4-tap-hold gesture, or automatically when the battery hits critical — powers down the microphone first and then puts the chip to sleep. If that last step failed, the Omi stayed awake with the microphone already switched off and no way to switch it back on, so it went on running, connecting and syncing as though nothing were wrong while recording absolutely nothing until it was restarted. Turning it off by hand — the 4-tap-hold gesture, or "Shutdown Omi" in the app — now restarts the Omi if the shutdown can't finish, which brings the microphone back along with everything else. The automatic low-battery shutdown deliberately does **not**: whatever stops a shutdown completing is usually still broken on the next boot, so restarting there would just loop a nearly-flat battery through boot after boot and never actually switch off. It stays up instead and lets the cell run down, which costs the microphone for the few minutes of charge that were left rather than wasting them. This became possible in `oo-2.6.0`, when the firmware first began switching the microphone's power off; before that it was always on and the failure could not occur. Requires firmware ≥ `oo-2.8.5`.
- **New (dev): the event log now records the microphone's input level, and survives the restart that matters.** Two gaps closed. First, "nothing was recorded" has always been ambiguous — a quiet room and a dead microphone look identical from the phone, since both produce no recordings and no files. The event log now tracks the loudest and quietest sound the Omi heard across each five-minute window, alongside the threshold in force, and reports it whenever that flips between silent and not — plus once an hour regardless. So a level pinned at zero (a wedged microphone) is distinguishable at a glance from a level bouncing around below the threshold (a genuinely quiet room), without a per-window entry crowding out the rarer records the log also has to hold. Second, the log's records at start-up — including the one saying how many pairing keys the Omi loaded, the only direct evidence of an unexpected unpairing — were being discarded every single time, because the log switches itself off at every restart and the app only switches it back on once it has connected, seconds later. Start-up records are now kept regardless. Dev builds only.
- **Fix: the Omi could go silently unreachable until you power-cycled it — it now recovers on its own within seconds.** Whenever the Omi disconnects it has to start advertising again, or the phone simply cannot see it. That restart could fail — most often for a moment right after a disconnect, while the Bluetooth stack was still letting go of the old connection — and the firmware neither noticed nor tried again. One failure and the device was gone: still running, still recording everything to its card, but invisible to every phone in the world until someone took the battery out or held the button. A two-hour outage on 2026-07-31 is what pinned it down: a second phone couldn't see the Omi either, a full phone Bluetooth reset changed nothing, and the device — which turned out to have been running for 33 hours straight without a single crash — reconnected the instant it was power-cycled. The firmware now re-asserts advertising on a timer whenever it isn't connected, so a failed restart is retried until it works and *any* way the radio can end up off the air heals within about half a minute rather than lasting until you notice. Nothing that was recorded during such an outage was ever lost; it just couldn't be collected until the device came back. Requires firmware ≥ `oo-2.8.4`.
- **Fix: the app no longer hammers the Bluetooth stack while the Omi is unreachable.** During an outage the app kept retrying roughly every 45 seconds for as long as it stayed open — about 80 attempts an hour — which is the exact pattern that gets Android's Bluetooth service itself into a bad state, and is why the native layer already backs off. The app now backs off too, stretching from 45 seconds to 12 minutes as an outage persists. Opening the app still tries immediately, so you never wait out a timer you can see; the backoff only governs the automatic retries happening while nothing is asking. Tapping sync or connect yourself was never throttled and still isn't.
- **Fix: New device features now appear right after a firmware update instead of waiting for a lucky reconnect (Android).** Android keeps its own copy of the Omi's Bluetooth service list and reuses it on every reconnect rather than asking the device again. That copy is what the app works from — so after a firmware update that adds something new, the phone could keep serving the old list and the app would simply not see the new capability, showing an old settings screen against new firmware with no indication anything was stale. It cleared up only when something happened to fully tear the connection down. The app now notices when the Omi's firmware identity has changed since the last connect and refreshes that copy once, immediately, by cycling the link — so a firmware update's new features are there the first time you open Settings. It runs only on the first connect after an update, never during a sync (it waits for the next connect instead of interrupting a transfer), and is skipped when the check itself can't be trusted. iOS handles this correctly on its own and is unaffected.
- **New: A "Connected LED" switch in Device Settings → Customization turns off the solid blue light the Omi shows while your phone is connected.** The blue indicator is on whenever the phone is in range, which for most of the day is *always* — so the Omi glows continuously, and the light that actually tells you something (yellow while recording, red while muted) never gets a chance to show, since the connected state overrode it. Switch it off and the connection stops driving the LED altogether: an idle connected Omi sits dark, and recording, mute, low-battery, and charging indications show through as they do when disconnected. It's stored on the device, so it survives app restarts and re-pairing, and defaults to on (the previous behaviour). Requires firmware ≥ `oo-2.8.2`; on older firmware neither switch appears. It sits under the new **"LEDs On"** switch (below), which governs whether any indicator shows at all.
- **New: "LEDs On" in Device Settings → Customization — the Omi's LEDs no longer forget themselves every restart.** The Omi's LED master switch has always lived only in memory: it starts **off** at every boot, and the only way to light the LEDs was the button gesture, which lasted until the next reboot or battery-out. So anyone who wanted indicators had to re-enable them by hand, over and over, and there was no way to see or set that state from the app at all. The new switch stores the choice on the device: turn it on and the LEDs come up on after every restart; leave it off and you get exactly the previous behaviour. It applies immediately as well as at boot, so flipping it does something you can see right away. The button gesture still works and still wins for the current session — it's a temporary override now rather than the only control, and a restart returns the Omi to whatever the switch says. Requires firmware ≥ `oo-2.8.2`.
- **New (dev): The event log now reports the Omi's pairing state at every boot.** When a device silently loses its pairing, the phone can only see the aftermath — reconnects that look healthy for a second and then drop, forever, with no way to tell whether the Omi still thinks it's paired. The event log gains a **"Bonds at boot"** record showing how many pairing keys the device actually loaded, flagged **"(device is UNPAIRED)"** when that count is zero, plus separate records whenever a wipe is *deliberate* (a post-update pairing reset, or the 5-tap-and-hold gesture). So an unexplained loss is now distinguishable at a glance from an intentional one, in the same log you already pull. Dev builds only, and requires firmware ≥ `oo-2.8.1`.
- **New (dev): An on-device diagnostic event log in Debug Tools.** The Omi's drop counters (`0x19B10062`) only tell you *how many* empty-bin rotations / marker drops / pause-gate saves happened since boot — not *when*, in what order, or with what context. On firmware built with the event log, Debug Tools gains an "Event log" card: a toggle enables a small on-device event ring that timestamps each of those health events (plus priority start/stop, session-end, and block/codec drops) with device uptime and cause context. The app drains and clears it on connect (and via a "Pull now" button), shows the records, and writes them into the saved diagnostic logs — so a lost Priority Recording can be pinned to the exact uptime and cause without an RTT debug cable. It's a developer tool: **off by default, not persisted on the device** (a reboot clears it until the app re-enables), RAM-neutral, and only appears when the connected firmware advertises the capability. Requires firmware ≥ `oo-2.8.0` built with the event log enabled.
- **Fix: "Delete Day" now clears the whole day — including short recordings, Priority Recordings, and discards you'd filtered or hidden.** With a duration filter active, Delete Day used to remove only the rows visible in the current tab, so a short Priority Recording (which lives under Hidden) or any filtered-out ghost rows survived the delete and reappeared later. It now removes everything for that date — recordings of any length, Priority Recordings, their markers, and every discard — regardless of the Main/Hidden/All filter or the ghost toggle, and the confirmation dialog spells that out. "Delete Discards" likewise now clears every discard for the day rather than just the ones showing in the current tab, and stays available whenever the day has any (so hidden ghosts remain deletable). Picking out individual items still goes through multi-select.
- **Fix: Deleting the last marker no longer strands you on an empty markers-only screen.** In the bookmarks-only view, removing the final marker (from the row list, the marker player, or a background sync that cleared it) left you looking at "No marked recordings yet" with the toggle gone and no way back. It now drops you back to the recordings list automatically once the last marker is gone.
- **Change: The markers-only (bookmark) toggle moved from the top bar into the Conversations header, beside the ghost and filter controls.** The three list-view controls now sit together as one right-aligned group, freeing space in the app bar. It behaves exactly as before and stays visible in the markers view so it's always the way back out.
- **Fix: A recording that only partly transferred during a *background* sync is no longer duplicated.** 0.30 stopped a half-transferred recording being scrambled, but only closed the hole on the foreground (Process / open-app) path. The background auto-sync used a separate processing routine that still decoded a partly-transferred file and deleted it — so when a Bluetooth drop cut a transfer mid-file (e.g. "Stream closed without EOT"), the app would keep the partial on the device, re-fetch the whole file on the next background sync, and process it *again* as its own recording. The result was two recordings sharing the same stretch of audio (a few minutes duplicated) and an extra split where there should have been one continuous recording. The background path now honours the exact same rule as the foreground: a file that hasn't fully arrived is left untouched until every byte is in, then processed once — which also removes the wasteful full re-download (the next sync resumes where it left off instead of starting over). Purely app-side; no firmware change, and recordings already on disk are unaffected.
- **Fix: Switching storage backend now reliably wipes and reformats the card, instead of occasionally coming back recording nothing.** The Switch-backend control was meant to reformat the SD every time, but the device only actually reformatted when it didn't already recognise the target layout — so after switching back and forth, the Omi could boot onto stale leftover metadata from the previous backend and capture nothing (an empty recordings list with every drop counter reading zero). Firmware `oo-2.7.4` makes the switch always reformat the target backend fresh on the next boot, and the confirmation dialog now says plainly that this **wipes the card — sync everything off first.** The picker also only offers the backend you're *not* on (labelled "Switch to Ring" / "Switch to LittleFS") and shows which one is currently active, so you can't accidentally "switch" to the backend you're already using — re-selecting the active backend is a firmware no-op now (no wipe), matching the reformat-in-place action that lives under Clear Storage. Requires firmware ≥ `oo-2.7.4`.
- **New: A ghost toggle on the Conversations screen hides the grey "discard" rows.** The VAD-dropped and muted stretches (the faint grey rows between recordings) can now be hidden in one tap: a ghost icon beside the Conversations header's filter — shown whenever there are any to manage — collapses every discard row out of the day list, and tapping it again brings them back. It's purely a view toggle: the discards themselves are untouched on disk and stay recoverable once shown again, and the setting sticks across app restarts. It's independent of the Main/Hidden/All duration filter, so you can hide ghosts without disturbing which recordings you're looking at.
- **New: An optional "Ring" storage backend that stops the Omi dropping audio during long offline recording.** The Omi's flash filesystem keeps no persistent map of free space, so once the card fills it scans the whole card to find room for each new block — a pass that stalls SD-card writes for seconds and drops audio, exactly in the all-day-offline case where the card stays fullest. Device Settings → Debug Tools now has a **Switch backend** control that reformats the card to a raw circular-log ("Ring") layout instead: recordings are appended end-to-end with an O(1) tail pointer, so no free-space scan ever runs and the write path keeps steady throughput no matter how full the card is. It is **opt-in** — the default stays the original filesystem — and switching **erases the card** (it reformats and reboots the Omi), so sync everything off first. Requires firmware ≥ `oo-2.7.0`; on older firmware the control doesn't appear. Still experimental: if the Ring backend can't mount, the device falls back to the original filesystem automatically so recording always continues.
- **New: Debug Tools shows which storage backend the Omi is running.** A "Storage backend" row at the top of the diagnostics card reads **Ring** or **LittleFS** (the original filesystem). It reports the *mounted* backend rather than just the one you selected, so it reflects the automatic fallback above. Requires firmware ≥ `oo-2.7.0`; older firmware shows a dash.
- **Fix: The sync progress card and the sync notification now always show the same count.** The recordings-screen status card ("N of M segments") and the persistent sync notification tracked progress with two independent counters, so in the slower gaps between files the card could blank back to "Scanning device…" while the notification kept counting. They now both read one shared progress figure owned by the sync engine, so they always agree and neither slides backwards mid-sync.
- **Change: The "Reset pairing after update" switch (Android) is hidden for now and defaults off.** Bonds are expected to survive a firmware update — the flash never reaches the memory that stores them — so the extra pairing reset shouldn't be needed, and leaving it on has its own failure mode (the phone-side bond clear can silently not take, stranding the reconnect). Firmware `oo-2.7.3` separately removes a needless pre-flash write next to the bond keys that was the suspected cause of a device occasionally returning from an update unpaired. The control is only hidden, not removed — if a genuine need resurfaces it can be brought back.

### 0.30

- **Fix: Background syncs no longer stall out and leave recordings stuck on the Omi.** When the app synced in the background (screen off), it would pull only a file or two and then a stall-detector would cut the connection — every time — so the backlog on the device grew through the day and larger recordings never came across until you opened the app. The cause: the background stall-detector judged "is this transfer still making progress?" from a signal the phone heavily throttles while the app is asleep, so a large file transferring perfectly fine looked frozen after 60 seconds and got cut off mid-transfer. It now judges progress from the actual bytes landing on disk, which the phone can't throttle, so only a genuinely dead transfer is cut — background syncs run to completion and the device drains as it should. As a side effect this also removes the repeated reconnects that had been contending with the Omi's own SD-card writes and dropping a few seconds of on-device audio. App-side fix; no firmware change.
- **New: Debug Tools shows how much device memory is spare.** The diagnostics card gains two rows fed by the firmware (`oo-2.6.2`+): "SD worker stack" and "Codec stack" show peak memory each thread uses against its budget, so it's clear how much is reclaimable (amber only if a stack is riding its ceiling). The SD-queue peak-depth row now reads out of the firmware's real queue limit (120 on `oo-2.6.2`+, 100 on older builds) instead of a fixed number. Older firmware shows dashes/zeros for the new rows.
- **New: Device diagnostics and charging state keep updating during a sync.** The Debug Tools diagnostics card (SD-drop and write-path counters, live uptime) and the battery charging indicator used to freeze for the entire duration of a recording sync — the app can't safely *read* those over Bluetooth while a transfer is running (the read races the sync stream and drops the link on Android), so it waited until the sync finished. Now the Omi *pushes* the drop counters as a live notification while you're looking at them — every couple of seconds during a transfer, which is exactly when the SD write-queue backs up and drops happen — and the charging state is no longer suppressed mid-sync. So you can watch the counters and uptime tick in real time as a sync runs, instead of staring at a frozen card. Requires firmware ≥ `oo-2.6.1`, and the live 2-second refresh now engages the instant a sync begins rather than lagging up to 15 seconds behind it (firmware ≥ `oo-2.6.3`). On the rare Bluetooth link too small to carry the pushed notification, the card falls back to a direct read so it keeps updating instead of sitting on "Reading drop counters…". Separately, the SD-queue **peak depth** row is now labelled "(since boot)" and shows the device's own high-water mark as-is — it's a monotonic since-boot peak, so it can't be delta-subtracted like the other counters, and "Zero all counters" leaves it (and the stack/uptime gauges) live rather than pretending to reset it.
- **Change: Companion Device Pairing is now on by default (Android).** Registering the Omi as an Android system "companion" exempts the app from the aggressive battery-manager freezing some phones apply, so when the Bluetooth link wedges the app can recover on its own — running its reconnect/recovery in the background — instead of sitting stuck until you toggle phone Bluetooth by hand. This is a bare association only; it does **not** re-enable the Companion *presence observation* that used to cause the opposite problem on OnePlus/Oppo/Realme (that was removed earlier and stays removed). Newly paired devices get a one-time system pairing dialog as part of connecting; existing setups are unaffected until you re-pair or toggle it. If your phone is one of the rare ones where a companion association makes reconnection *worse*, turn **Companion Device Pairing** off in Settings → Debug Tools — the toggle still applies immediately in both directions.
- **Fix: A recording that only partly transferred is no longer silently scrambled.** When a transfer from the Omi came up short (a Bluetooth drop mid-file), the app kept the partial recording on the device so it could resume it on the next sync — but the processing pass, which only knows what is on disk, went ahead and decoded that half-file and then deleted it, as it does with every recording it finishes with. The resume then had nothing to continue from, so the remaining audio was written to a fresh file as though it were the *start* of the recording. Two syncs later the file reached exactly the length the Omi advertised — that outcome was arithmetically guaranteed, not a fluke — so it passed the "did we get it all?" check, and the intact copy on the Omi was deleted. The recording was left holding its own ending twice and missing its beginning. The app now leaves a partly-transferred recording alone until every byte has arrived and processes it once it is whole (usually on the very next sync, with no delay), and a resume is always checked against what is really on disk rather than trusting the saved position. **If you have a recording from before this release that plays back garbled or jumps around, this was almost certainly the cause; the original is unfortunately gone.**

Either way, an in-progress recording not yet written to the SD card may lose its last few seconds. Requires firmware ≥ `oo-2.6.0`.

A failed update leaves everything paired exactly as it was (the old firmware, which the device falls back to, ignores the flag). Requires firmware ≥ `oo-2.6.0` for the device-side wipe; on older firmware only the phone side is cleared. iOS doesn't offer this (an app can't clear a system pairing there).

### 0.29

- **Fix: The Omi no longer loses a Priority Recording's start or stop marker when it happens to be pausing its SD-card writes.** Root-caused with the diagnostics counters below: the firmware pauses SD writes during silence to save power, and the internal start/stop marker for a Priority Recording could be silently discarded at that pause the instant a recording started or stopped — losing the whole recording (start dropped) or leaving it stuck open and swallowing later audio (stop dropped). The firmware now always writes a marker through the pause (a pause is a power optimization, not a reason to drop a marker), so the boundary is preserved. Requires firmware ≥ this release (`oo-2.5.9`). This addresses the on-device cause the app-side auto-close (below) was compensating for.
- **New: Debug Tools shows two counters that pin down where a Priority Recording's stop marker goes.** "Session-end marker emits" (how many times the firmware's stop path fired) and "Markers kept at SD pause gate" (marker data written through a pause instead of dropped — before `oo-2.5.9` these were the silent loss). Read together with the existing counters they show, from the diagnostics screen alone, whether a missing marker was never written by the firmware or was written and then dropped on the way to the SD card — no debug-cable capture needed. Older firmware shows 0. The measurement costs ~8 bytes of device memory and no extra logging.
- **Fix: A stopped Priority Recording that the app didn't get the stop for now closes itself instead of staying stuck "in progress" and swallowing later audio.** When the Omi drops the internal stop marker for a Priority Recording (it can still happen — see below), the app used to keep the recording in force-capture mode indefinitely, showing a "conversation in progress" banner and merging every following automatic recording into that one runaway recording until a multi-hour timeout or a device restart. The app now recognizes the tell-tale sign that the device already stopped on its own — a genuine silence gap, which true force-capture never produces — and finalizes the stuck recording at that point automatically, so following audio is captured as normal separate recordings. As additional safety nets: the app stops trusting an open Priority Recording once it has run past *your* Priority Recording safety-cap setting (plus a margin) rather than a fixed six hours (tighter for the common 120-min cap, and no longer truncating a legitimately long recording when you've set a large cap), and the firmware now tries harder to always write the stop marker when a recording ends (previously it was skipped if an acoustic wake had momentarily cleared the "recording" flag). The underlying on-device marker drop this was compensating for is now fixed directly in the firmware (see the SD-pause-gate fix above); the app-side auto-close remains as a belt-and-suspenders recovery that works on any firmware.
- **Fix: An Omi that shows "connected" but has stopped syncing now recovers on its own instead of needing you to toggle Bluetooth (Android).** Occasionally the phone's Bluetooth link to the Omi would wedge — the app still showed the device connected, but every attempt to list or pull recordings silently came back empty, so sync sat reporting "no new segments" until you turned Bluetooth off and on by hand. The app now detects this dead-but-connected state (a stalled transfer, or a storage command that times out) and automatically recycles the connection — dropping just that wedged link and rebuilding a fresh one, the same thing toggling Bluetooth does — so syncing resumes without you noticing. In the background it recovers silently; markers and Priority Recordings ride through untouched. Relatedly, a wedged link can no longer cause a perfectly good recording to be deleted from the Omi: a transfer that fails because the *connection* is dead (rather than the file being unreadable) no longer counts against the file's drop budget, so it is retried on the fresh link instead of being discarded. Entirely an app-side fix; no firmware change.
- **New: The debug log records the Omi's SD-write drop counters and live uptime on every connect.** With "Save Debug Logs to File" enabled, each connection now logs how many audio blocks/frames the device has dropped since boot and how full its write queue has run, plus the device's *true current* uptime — which makes it possible to tell a recording that was *dropped on the device* apart from one that was *never captured*, from the log alone. Relatedly, the existing device-diagnostics line was corrected to label its figure as the **previous session's** runtime before the last reset (not current uptime), and it's no longer repeated on every connect.
- **Fix: A Priority Recording that is still running when the app syncs no longer loses its red flag or gets chopped up.** If you started a Priority Recording (automatic mode) and it was still going when the app pulled recordings from the Omi — because you tapped Sync, or a background sync ran mid-recording — everything captured *after* that sync was processed as an ordinary automatic recording: it could be split on silence, have quiet stretches dropped, and lose its red "Priority Recording" marker. The app now remembers that a Priority Recording is open across syncs and keeps capturing it as one continuous, force-captured recording — no silence splitting, flag preserved — until you stop it. This also applies to the single-button Toggle. If the Omi restarts mid-recording the Priority Recording is ended at that point (the firmware doesn't resume it after a reboot), and a stop that never arrives can no longer leave the app force-capturing indefinitely (it releases after a few hours).
- **New: The Debug Tools diagnostics card reports Priority Recording counters.** Next to the existing Bluetooth and SD-drop counters, four new figures — Priority recordings started and stopped, marker writes dropped, and empty bin rotations — make it possible to trace a Priority Recording that silently reverted to a normal recording from the app itself, without attaching a USB debug capture. Requires firmware ≥ this release; older firmware reports zero.
- **Change: A cleared Bluetooth outage now recovers within minutes instead of waiting for the next scheduled sync (Android).** In 0.28 the app stopped constantly retrying once a long outage was confirmed and handed reconnection to the sync schedule — good for battery, but if the Omi came back into range (or your phone's Bluetooth recovered) a minute later, the link wasn't picked up until the next scheduled sync, up to a full sync interval away (typically 30 minutes). The app now follows the hand-off with a short burst of reconnect attempts that start a couple of minutes apart and back off (roughly 2, 4, 8, 16 minutes) before settling onto the normal sync interval — so a wedge that clears is reconnected within minutes, while a device that's genuinely gone (switched off, left at home) quickly tapers to the battery-friendly interval after only a few extra attempts. Opening the app still reconnects immediately, as before. Relatedly, the "toggle Bluetooth to reconnect" check for a device that walks back into range but still can't be reached is now re-run on a time schedule (about every 15 minutes) rather than after a fixed number of failed attempts — which, now that attempts are spread out, could otherwise have stretched to many hours.

### 0.28

- **Change: The app stops hammering Bluetooth reconnect attempts during a long outage, to save battery (Android).** When the phone can't reach the Omi, the native service used to retry the connection roughly every 30 seconds for the *entire* length of the outage — potentially hours — draining the battery for nothing, since your recordings are safe on the device and can't be pulled until the link recovers anyway. Now, once an outage is confirmed (after the first several quick retries, which still recover brief blips instantly and still trigger the "toggle Bluetooth" check), the app stops the constant retrying and falls back to its normal sync schedule — trying roughly once per sync interval in the background, and promptly whenever you open the app. This restores the battery-saving intent of the sync interval, which the constant native retrying had been quietly overriding. (0.29 restores quick recovery of a *cleared* outage on top of this.)
- **Fix: The app no longer throws away a hard-won reconnection after a long Bluetooth outage (Android).** When the phone's Bluetooth stack gets stuck and can't reach the Omi for a long stretch, the app keeps retrying in the background. If it finally reconnected while the app happened to be in the background, a power-saving check would immediately drop the link again — because no sync had been explicitly scheduled for that exact moment — so the outage dragged on until you toggled Bluetooth by hand, even though the connection you needed had briefly been in hand. Now, if recordings are actually due to be synced (which they always are after a long outage), the app keeps that reconnection and syncs on it instead of discarding it. If nothing is due, it still drops the link to save battery, exactly as before.
- **Change: Connection-outage debug snapshots now tell a rejecting Bluetooth stack apart from a fully stalled one.** The outage record already logged the app's own give-up timeout; it now also keeps the last real error code the phone's Bluetooth actually reported during that outage. This separates an outage where the phone's stack was actively refusing the connection (a real error code) from one where it went completely silent (only the app's timeouts, with the system never reporting anything at all) — two different failures that previously looked identical in the log.
- **Fix: A large recording that only transfers a bit at a time is no longer dropped as "unreadable" (Android).** To keep one genuinely-corrupt file from blocking the sync queue, the app gives up on a recording after several failed transfer attempts and deletes it from the device. But a big recording that comes down in pieces — because Bluetooth is throttled in the background, or the link keeps dropping mid-transfer — could rack up those failed attempts even while it was steadily making progress, and get deleted just short of finishing. The app now only counts an attempt against a file when the transfer made *no* forward progress; any recording that is still advancing keeps its slate clean and is retried until it completes (it typically finishes once the app is in the foreground). Only a file that repeatedly delivers nothing is dropped.
- **Fix: A recording is no longer deleted from the Omi when its transfer comes back empty.** During sync the app pulls each recording from the device and, once it has it, deletes it from the Omi to free space. If the device reported a recording's size but then returned no data for it — a transient read glitch that can happen just after the device rotates to a new file, such as around a Priority Recording — the app treated the empty transfer as "done" and deleted the recording anyway, losing it for good. The app now checks it actually received the whole file before deleting; a short or empty read is kept on the device and retried on the next sync. A recording that keeps coming back empty is dropped only after several attempts, so one unreadable file can't stall the rest of the queue.
- **Fix: The firmware-update screen no longer gets stuck forever on "Installing firmware… 0%".** On the local-file flash path, if the update failed or the Bluetooth transfer wedged before any data moved (for example the link was still busy finishing a sync), the progress screen could sit on 0% indefinitely with no way forward except backing out and retrying. The update now detects both a reported failure and a silent stall (no progress for 45s), stops cleanly, and returns you to the update screen with an error message so you can tap to retry.
- **New: "Single recording button" — one button that toggles recording.** Button Configuration has a new switch at the top that collapses the separate Start and Stop recording actions into a single **Toggle** action: one gesture starts a recording if none is running and stops it if one is. It works in both modes — in manual it toggles your recording, in automatic it toggles a Priority Recording — and applies to whichever gestures you map it to. Flipping the switch on converts an existing Start gesture into the Toggle (and drops the now-redundant Stop); flipping it back off clears the recording gestures so you reassign Start and Stop deliberately (this avoids accidentally leaving a Start with no Stop). If you turn it off while a manual recording is in progress, the app warns first, since you'd be removing the button that stops it. There's also a new warning in split (Start/Stop) mode if you've mapped Start but not Stop — in automatic mode it notes the recording still ends at the safety cap. Requires updated firmware; on older firmware the Toggle option doesn't appear.
- **Fix: A short "below minimum speech" ghost no longer flickers in under "Conversation in progress."** When a brief bit of speech was captured while a conversation was still open, the list could show a greyed-out "below minimum speech" row at the same time as the "Conversation in progress" banner above it — reading a slightly *later* time than the banner, which looked contradictory. That row is now hidden while it can still be folded back into the open conversation (i.e. if you keep talking within your silence-to-split window), and it reappears on the next sync only if it truly ends up as a separate dropped stretch. Display-only: nothing is deleted, and the row is always still visible in the Hidden/All filter tabs.
- **Fix: The app no longer runs a maximum-power Bluetooth scan while it is trying to connect (Android).** When a connection took more than 5 seconds, the app started a continuous, unfiltered Bluetooth scan alongside the connection attempt, then threw the scan's results away. A Bluetooth link has to be established within the first fraction of a second or the phone abandons it, and that scan was competing for the radio during exactly that window — so it only kicked in once a connection was already struggling, and then made it likelier to fail. Removing it should reduce the "Connecting…" loops, especially when other Bluetooth devices (watches, earbuds, glasses) are connected.
- **Fix: Connection failures are now reported accurately instead of being masked (Android).** The app gave up on a connection attempt before Android had finished reporting why it failed, so every failure was recorded as a generic timeout and the real cause was never logged. The app now waits for the actual reason. This also corrects the 0.27 "ghost link" behaviour below: measurement showed the Omi holding **no** connection at all during these outages, so the app no longer performs a speculative dummy connect-and-close against a device that isn't holding anything — that was adding Bluetooth churn to connections that were already failing. Ghost-link flushing still happens when a leftover link genuinely exists. The one-time "Omi can't reconnect" notification now triggers on any run of failed attempts rather than only on the misidentified signature — but first the app listens for your Omi, and stays quiet if it can't hear it, so an Omi that is simply out of range or switched off no longer tells you to go toggle Bluetooth. If it hears nothing, it listens again a few attempts later, so an Omi that was out of range when the outage began and comes back to a phone that still can't reach it does get the notification. (If that check can't run at all — Bluetooth off, scan permission missing — the notification behaves as it did before, since silence there would mean nothing. If the phone merely refuses the scan at that moment, the app draws no conclusion and asks again a few attempts later rather than guessing either way.) It also no longer counts a connection as recovered until the link has actually carried data, so the repeated "connects, then stalls" loop is now recognised as the outage it is instead of resetting the count each time — and the retry pacing backs off through that loop as well, instead of restarting at its fastest interval on every half-connection.
- **New: Device Settings → Debug Tools reports links that die at establishment.** A "Died at establishment (0x3e)" counter sits next to "BLE connect failures". It counts connections that came up and then collapsed before exchanging any data — the signature of the "Omi is visible but won't connect" outage, which the existing counter structurally could not see. If your phone reports these failures while this counter stays at zero, the Omi never heard the connection requests and the phone is at fault; if it climbs, the Omi did. Requires firmware ≥ this release; older firmware reports zero.
- **New: Connection outages are recorded to the debug log while they are happening (Android).** Previously the only way to see inside one of these outages was to notice it, attach a USB cable and run developer tools before it cleared — impossible for an outage that starts overnight. With "Save Debug Logs to File" enabled, the app now writes a snapshot the moment it gives up on the sixth consecutive connection attempt: what else the phone's Bluetooth was doing, whether any leftover link to the Omi existed, and — the useful part — whether the phone can still hear the Omi advertising, measured with a short scan right then. A second entry records how long the outage lasted once it clears. The result is a self-contained record in "Save Diagnostic Logs to File" that no longer depends on catching the failure live. That same scan is what decides whether the "toggle Bluetooth" notification is worth showing you, so it runs whether or not logging is enabled.
- **Fix: "Last synced" and the sync notification no longer treat a skipped sync as completed.** The "Last synced …" line under the Conversations header now tracks only syncs that actually pulled data (complete or partial) — a cycle skipped because the Omi was out of range or Bluetooth was off no longer resets it, so it always reflects how current your recordings really are. Relatedly, tapping Sync while the Omi is unreachable previously settled the notification to "Last Sync: Complete" at the current time even though nothing was pulled from the device; such a run is now recorded as a skip ("Last Sync: Skipped"), matching how automatic background syncs already report skips, and it leaves the "Last synced" time where the last real sync put it.

- **Fix: A reboot while muted no longer drops the audio recorded after it.** If the device rebooted (e.g. the battery died) while it was muted or had just been stopped, the app could keep treating the fresh recording session that came up afterward as still-muted and silently drop its audio, with no trace. The app now recognizes a brand-new recording session and keeps its audio.
- **Change: The app reads the recording mode from the device instead of overriding it.** The recording on/off state and the AAD sensitivity live on the device, which keeps them across a reboot. The app now reads that state when it connects (and after a device button tap) and reflects it, and only writes a setting when you change it yourself in the app. So a recording you started or stopped with the device button while your phone was away is no longer overwritten on the next connect.
- **Change: A discard's shown length is now the audio it actually contains.** A discard row used to show its wall-clock span, which could include long stretches where the device was asleep and recorded nothing (or, for a merged row, the gaps between separate noise stretches) — so a row could read far longer than the clip you'd get back. It now shows the length of the audio the device actually recorded, which matches the clip Recover produces. Real recorded silence is still included; only the device-asleep gaps are excluded.
- **Fix: Recovering one discard no longer deletes audio another discard needs.** Two discarded stretches often share a single ~5-minute raw segment (one owns the front of it, another the back). Recovering the first one deleted the whole segment, so when you went to recover the second it found nothing left and vanished with no recording produced. Recovery now preserves any segment still referenced by another discard, so each can be recovered independently.
- **Fix: Recovering a discard now works while the "Completed" banner is showing.** Tapping Recover during the brief green "Completed" banner (the ~10 seconds after a sync/process finishes) used to do nothing — the tap was silently dropped, and only a second tap once the banner cleared went through. The banner is a settled state, not a busy one, so Recover now dismisses it and proceeds immediately. If a sync or processing pass is genuinely still running, you get a "Finishing sync — try again in a moment" note instead of a silent no-op.
- **Fix: Muting or stopping right after a marker no longer leaves a stray clip.** A button-tap marker opens a ~50-second "guaranteed save" window so the tapped moment is kept even when it's quiet. Muting (or a manual-mode stop) inside that window correctly finalizes the marked clip — but the window used to linger past the mute, so a quick unmute or restart within the original 50 seconds could force-save a stray, marker-less snippet of near-silence that voice detection would otherwise drop. The window now ends at the mute/stop boundary, so only the intended marked clip is saved.
- **Fix: "Recover to Recording" no longer pulls in neighboring audio.** A discarded stretch usually shares a single ~5-minute raw segment with the recording right before or after it. Recovering it used to reprocess that whole segment, so the recovered clip swallowed the neighbor's audio — coming out far longer than the discard and overlapping the existing recording. Recovery now re-derives only the discarded slice itself, anchored at its real start time. When several back-to-back discards collapse into one ghost row, recovery keeps each one's exact byte span separate instead of merging them into one span that bridges the gap — so a real recording sitting between two noise stretches in the same segment is no longer swept into the recovered clip. Recovery also stops padding the silent gaps inside a discard, so the recovered clip's length matches what the ghost row reports (a "24-second" discard recovers as ~24 seconds, not minutes). (Discards are recorded with their exact byte span going forward; older discards from before this change still recover the whole segment.)
- **Fix: Force Process no longer rewrites your already-finalized recordings.** The debug **Force Process** button used to re-derive your entire history from raw segments on every run — overwriting finalized recordings (re-stitching adjacent audio and shifting their boundaries) and getting slower as segments accumulated. It now skips audio already covered by an existing recording, exactly like the normal Process button and background sync do. The old "rebuild everything from saved segments" behavior moved to a separate, confirmation-gated **Reprocess All from Segments** button in Adjustment Mode, so a full re-cut is now a deliberate choice rather than a side effect of pressing Force Process.
- **New: A banner warns when on-phone voice detection falls back to the device.** If the phone-side voice-detection model (Silero VAD) can't load during a sync, processing silently falls back to the device's own acoustic detection, which treats every frame as speech and can split recordings oddly. The recordings screen now shows an orange "Voice detection unavailable — using device fallback" banner while that fallback is active, and it clears itself automatically on the next healthy sync.
- **Fix: Guard against a flood of tiny junk recordings.** A clock-anchor mismatch on the device could make every post-silence resume marker read as a huge time gap, spraying out hundreds of one-frame recordings (one report hit ~3,500 in a minute). While the app is on device-fallback detection and sees a sustained run of these sub-second splits, it now coalesces further resume markers onto a single recording instead of splitting on each one. A lone short note still stands on its own — only a genuine flood is collapsed.
- **Fix: Recordings no longer lose track of their source segments.** Hardened how a recording records which raw segments it was built from — it no longer drops a segment reference on unusual path forms (which previously left a recording listing no source segments) — and a recording's saved metadata is now stamped with the correct session id even when that id was reset across a stitch. Also, "Copy Bins for Reprocessing" in Adjustment Mode now reports how many segments it copied (with a snackbar and refreshed folder count) instead of running silently.
- **iOS: more chances for background auto-sync to fire.** Alongside the existing background-sync task, the app now also registers an iOS *app-refresh* task — which iOS grants more often, and without waiting for the phone to be charging. Both honor your auto-sync interval as a floor. This only raises the odds of an opportunistic background sync; iOS still decides when (or whether) to actually run them, so it's a best-effort improvement, not a guaranteed schedule. Battery is unaffected — the Omi still stays disconnected between syncs exactly as before, and there's no continuous connection or background-audio trick involved. Android is unchanged (it already wakes on schedule via WorkManager/alarms).
- **Fix: Sync notification reliably stops sticking on "Connecting…" (Android).** The 0.24 watchdog only recovered *after* the process thawed, which under a long Doze could be many minutes away — so a scheduled sync that started connecting could still leave the notification stranded on "Connecting…" for the better part of an hour. The app now holds a CPU partial wake-lock for the whole connect attempt, so the OS can't freeze the process mid-connect in the first place; the normal "settle back to the idle Last Sync line" then runs on schedule (~150 s) and you see "Skipped" instead of a stuck "Connecting…". The wake-lock is reference-counted natively, so it never disturbs a concurrent firmware update or recording-processing run. As a backstop for the cases the wake-lock can't cover — the app's UI engine getting torn down by the OS overnight while the background service keeps running, which leaves no Dart code alive to settle the line — a native alarm now does it instead: it runs even in deep Doze with nothing else alive, and reverts a stranded "Connecting…" to the real "Last Sync: Skipped" line on its own (within ~150 s, or by the next scheduled sync at the latest), recording the skip at that point so the recovered line reads correctly even if the app was frozen the entire time. iOS is unaffected (it has no persistent connection notification).
- **Cancel an upload from the recording's Integrations list.** A recording with an upload actually in flight or waiting its turn now shows a **Cancel** button (in place of the old static "Waiting…"). If it's the only thing active for that integration, tapping Cancel just stops it; if a queue is backed up behind it, you're asked whether to cancel **This Recording** or the **Entire Queue** (tap outside the dialog or press back to keep everything). While an in-flight upload winds down to its next stopping point the row shows "Cancelling…" and hides the button so you get feedback and can't tap it repeatedly. An in-flight Omi Cloud upload stops cleanly between chunks (already-uploaded chunks are kept); a HeyPocket upload already mid-request finishes. (An auto-upload you cancel this way may come back on the next auto sweep while Auto-Upload is still on; a manual one stays cancelled. The button is hidden during the brief auto-retry window, where there's no in-flight or queued job to stop.)
- **Turning off an integration now stops its uploads immediately.** For Omi Cloud / HeyPocket, switching off **Auto-Upload** cancels in-progress and queued *auto* uploads (an explicit manual upload you started keeps running), and switching off **Enabled** cancels *everything* for that integration — in-progress and queued. Previously, turning off Auto-Upload left uploads running entirely, and turning off Enabled only dropped the queue while the active upload kept going. A chunked Omi Cloud upload stops cleanly between chunks (already-delivered chunks are kept and the rest resume if you switch it back on); a cancelled upload is not counted as a failure. (A HeyPocket upload already mid-request finishes, since a single request can't be interrupted once sent.)
- **iOS: the screen no longer sleeps mid firmware update.** A firmware (OTA) install now holds the screen awake — plus an iOS background-execution assertion — for the whole flash. Previously nothing kept the display on, so if it auto-locked the app dropped to the background and iOS suspended the Bluetooth transfer mid-update, which could leave the device in a bad state. The wakelock is released as soon as the update finishes, fails, or you leave the screen (and respects "Keep Screen On" if you have it pinned).
- **iOS: faster SD-card sync.** Incoming Bluetooth packets are now parsed and written to disk off the CoreBluetooth delivery thread, so iOS is no longer blocked from handing over the next batch while a packet is being saved — the transfer pipe stays full instead of stalling once per packet. Paired with the firmware change below, iPhone sync is substantially quicker.
- **iOS: background auto-sync wakes when the Omi comes into range.** Using CoreBluetooth state preservation & restoration, iOS relaunches the app in the background when your bound Omi returns to Bluetooth range and runs a sync if one is due — gated on your auto-sync interval, so Manual Only and not-yet-due wakes stay quiet. This is far more dependable than relying on iOS's opportunistic background-task scheduler alone, which fires unpredictably. Android's existing behavior — waking on schedule regardless of whether the device is in range — is unchanged.
- **iOS: recording processing isn't killed the instant you background the app.** The decode/VAD pass now holds an iOS background-execution assertion for its bounded window; a decode that outruns that window resumes on the next sync via the existing draft pipeline, so nothing is lost.
- **iOS: Bluetooth no longer drops at random mid-sync.** The heartbeat that stops the Omi from idle-disconnecting now runs natively in the CoreBluetooth layer instead of from a Dart timer, which iOS stops firing reliably once the app is backgrounded. Previously, in the gap between files of a multi-file sync the heartbeat could go silent long enough for the device to drop the link, abort the transfer, reconnect, and repeat. The native heartbeat keeps the link up between files so a background sync runs to completion — matching Android's existing behavior.

## Firmware

### oo-3.0

- **Change: the radio idles between transfers instead of running flat out.** The connection was negotiated once, for the speed a file transfer needs, and stayed there for as long as it was up — waking the radio about ninety times a second even with nothing to send, which is most of the time a connection exists. It now runs at that speed only while a recording is transferring or a firmware update is being flashed, and at roughly a tenth of it otherwise.

- **Fix: the Omi no longer hangs up on a phone that is still pairing.** An update deliberately clears the pairing on both sides, and until a new one is established the phone cannot send the signal that tells the Omi the link is in use — so the Omi read the silence as an idle phone and hung up, repeatedly, each time interrupting the pairing that was in progress. It now recognises an unpaired link and waits, up to a limit, so it still hangs up on a phone that has genuinely stopped talking.

- **Change: the Omi waits a minute before hanging up on a quiet phone, rather than fifteen seconds.** Fifteen seconds was short enough that ordinary things — pairing, setting up a connection — kept getting caught by it, and with the radio now idling cheaply between transfers there is little to gain from being quick about it.

### oo-2.10

- **Change: a marker tap does nothing while Manual Mode is idle.** It used to write a bookmark and force the microphone to capture for about a minute — in the mode whose entire promise is that it records only when you tell it to. With nothing being recorded there is nothing to bookmark, so nothing is written now: no bookmark, no empty bookmark entry, nothing. Markers tapped **during** a manual recording still work exactly as before. Automatic Mode is untouched, where that one-minute guarantee is deliberate: you can't tell whether the Omi rated the moment as speech, so the tap asserts that it did.

- **Fix: a manual recording starts where you pressed the button, not where the Omi caught up.** With the microphone now switched off in Manual standby (below), a recording began at the moment the firmware worked out what your press meant — and that takes about three quarters of a second, because it has to wait to see whether you're going to tap again. The microphone now wakes the instant the button is touched, so by the time the recording opens it already has that audio and can include it. Press the button for something else — mute, a bookmark, a pocket press — and the microphone simply goes back to sleep a moment later. Starting a recording from the app rather than the button still begins at the tap: there's no press to wake on.
- **Change: starting a Priority Recording no longer briefly interrupts the microphone.** Each one used to stop and restart the mic first, which was worth doing when that also power-cycled the part and could clear a fault. It hasn't done that since `oo-2.8.5`, so all it did was discard the fraction of a second in flight at exactly the start of the recording. The check it was there for is now done properly instead: the Omi verifies audio actually resumed and reports it if not.
- **Fix: a quiet Omi no longer advertises at full rate all day.** The radio advertises quickly after starting up and after every disconnect so your phone can find it, and only slows down once a recording ends. A device that started up in a quiet room never had a recording end — so it kept advertising at the fast rate indefinitely, for no benefit. It now settles to the slow rate a minute later if nothing is recording. Diagnostics also report the live advertising rate for the first time, so this is something you can actually check rather than take on trust.
- **New (dev): the Omi reports whether its microphone is actually delivering audio, and how much of the day it records.** Diagnostics gain two readings: how long since the last audio frame (so a stopped microphone is visible immediately rather than inferred from an absence of log entries) and total recorded time against uptime, which is the share of the day being captured. The event log also records every time capture is switched off or on, including a resume that failed or came back silent — so a quiet log can be told apart from a dead microphone. Event entries no longer tag themselves with a storage backend that was removed in `oo-2.9.0`.

- **Change: in Manual Mode the Omi now switches its microphone off while it isn't recording.** Manual standby is the resting state for most of the day, and in it the microphone cannot start anything — only the button or the app can — yet it was still being clocked and listened to continuously, which is one of the largest constant draws on a 150 mAh battery. It now stops when you stop a recording and starts when you begin one, from wherever the instruction comes: the button, the app, a restart into a state you left it in, or the safety cap ending a long recording. **One thing changes for you:** a manual recording used to include roughly the last second of sound from *before* you pressed the button, and it can't any more — there is nothing being captured to include. Recording now begins at the press. Bookmarks work only while a recording is running — in standby there is nothing to bookmark, so the tap does nothing at all (see above). Automatic Mode is unaffected — it has to keep listening to know when to record — and muting behaves exactly as before.
- **Fix: recordings made after unmuting were stamped with the wrong time.** Muting stops the microphone, so nothing is captured until you unmute — but the Omi kept counting the recording clock as though the audio had continued, so everything captured after an unmute was timestamped *earlier* than it happened, by however long you stayed muted. A long mute could therefore file a recording under the wrong hour, or even the wrong day. The Omi now marks the gap so the timeline is re-anchored the moment sound returns. As a side effect it also fixes a smaller oddity: up to a second of sound from *before* the mute could be replayed into the recording that followed it.

### oo-2.9

- **Change: the Omi clears its own Bluetooth pairing after every firmware update.** Flashing rewrites the memory region the pairing keys sit beside, and a key that doesn't survive it leaves the Omi in a state it cannot get out of on its own: it holds a pairing slot, and it refuses any new pairing while that slot is occupied — it has no way to tell a working key from a damaged one. The phone can't clear it either, so the only escape was the five-tap-and-hold gesture. The Omi now notices for itself when a firmware image has finished transferring (no involvement from the app, so there's nothing to go wrong in between) and clears its pairing on the next start-up. The app clears its side at the same time, so the two pair again cleanly. This runs after every update, including reinstalling the same version, since the same memory is rewritten either way. An update that is cancelled or fails mid-transfer never triggers it. An ordinary restart, and the Reboot command, never trigger it either. Installing *this* update also resets the pairing once on its own — the update that carries the change is necessarily installed by the older firmware, which doesn't yet know to do it — so expect to reconnect once after it lands. **Removed:** the `0x18` arm-unpair command, which the app used to send before flashing — the Omi no longer needs to be told.

- **Change: the original filesystem storage backend is gone; the Omi records only to the Ring log now.** The two backends have coexisted since `oo-2.7`, selectable from Debug Tools, and Ring has been the better one on every measure that matters: it does not stall the write path scanning the card for free space (the reason audio frames were dropped on a near-full card), and since `oo-2.8` it costs the same idle current. Keeping both meant carrying a filesystem that was only ever going to be the fallback, so it has been removed. This frees **29 KB of RAM** — the filesystem's caches and open-file handles — taking the main chip from 97% of its memory to 91%, plus 24 KB of program space, which is the headroom the next round of work needs. **⚠️ If your Omi is still on the original filesystem, sync everything before installing this update: the first boot after it will reformat the card to a Ring log, and anything not yet synced is lost.** An Omi already on Ring keeps every recording and notices nothing. The card format, the sync protocol, and the app are all unchanged.
- **Fix: a stumbling SD card no longer costs you audio silently, and a wedged one now recovers by itself.** When a write to the card failed, the Omi backed off for two seconds before retrying — and every audio block that arrived during that pause was thrown away without being counted, so the card could be losing seconds of audio at a time while the diagnostics still read zero. Those seconds are now held in memory and written once the card comes back, which covers a fault lasting up to about eight seconds; anything genuinely lost past that is counted, so the drop readings finally tell the truth about a failing card. Separately, some card faults are not transient at all — the card's controller can latch up in a way that no amount of retrying clears — and the Omi would go on retrying every two seconds indefinitely, recording nothing until someone noticed and restarted it. After three failed retries it now powers the card down and brings it back up, which is what actually clears that state, and resumes recording in a fresh segment. It never reformats while doing so, so recordings waiting to be synced are safe. Both behaviours existed on the old filesystem backend and were missing from Ring; this restores them.
- **Removed: the switch-backend command (`0x1A`).** With one backend there is nothing to switch to; the storage-status byte still reports which backend is mounted, so the app's Diagnostics panel is unaffected. The read-resume offset file the filesystem kept on the card is gone too — the ring has tracked the sync position from the phone's own record since `oo-2.7`, and the command that maintained the file has done nothing at all on Ring ever since.

### oo-2.8

- **Fix: the Ring storage backend no longer costs more battery than the original filesystem.** Writing audio to the card means powering up the SD bus, and Ring was doing that for *every* audio block — about twelve times a second — even though roughly nine blocks in ten are only gathered in memory and write nothing. The original filesystem never did this: it collects several seconds of audio in RAM and wakes the bus once, when it actually has a batch to write. That difference barely shows while the phone is connected, but with the phone away — which is most of the day, since the Omi hangs up on an idle connection after 15 seconds — it worked out to roughly a hundredfold difference in how often the bus was powered up, and it is why a day on Ring came up short against the same day on the original filesystem. Ring now wakes the bus only when it genuinely writes, and gathers audio to the same depth before doing so, so the two backends should cost the same idle current. Nothing else changes: recordings, syncing, and the contents of the card are untouched, the update does not reformat anything, and the original filesystem behaves exactly as before.
- **Fix: a recording could end with a few seconds of stale audio if the Omi lost power at the wrong instant.** When one recording ends and the next begins, the device records the finished recording's length on the card. That length could be written before the last of its audio had actually reached the card, so an unlucky power cut — battery going flat mid-rotation, on a card that was already failing writes — could leave a recording claiming a few seconds more than it really had, and playing back whatever happened to be in that space. The length is now always written after the audio it describes, so a recording can only ever claim data that is genuinely there. Rare in practice, but it needed an actual write failure to become possible at all, and the window widened with the batching change above.
- **New: The LED master gate has a persisted boot value (`0x19B10082`).** `is_led_enabled` is volatile RAM toggled by `BUTTON_ACTION_TOGGLE_LED`, so it reset to off on every boot and no reboot could ever come up with LEDs on. `main.c` now seeds it from a stored setting right after `app_settings_init()` — before `button_init()` starts the only other writer — defaulting to 0, the previous behaviour. A BLE write applies to the live gate as well as the stored default so the app's switch acts immediately; a read deliberately returns the **stored default rather than the live gate**, since the button gesture is a session override and a live-tracking read would make the app's write-then-verify contradict what it just stored.
- **New: The connected (solid blue) LED can be turned off.** A new LED service (`0x19B10080` / char `0x19B10081`, 1 byte, capability bit `1<<13`) persists whether a live phone connection lights the LED solid blue. With it off, `is_connected` no longer participates in the LED state machine at all, so the branches below it — manual/auto recording (yellow), and the mute / low-battery / charging indications above it — show through instead of being masked for as long as the phone is in range. Defaults to on, so an updated device behaves exactly as before until the app writes it. It is deliberately its own service registered **last**, not a seventh Settings characteristic: the Settings service is registered first, so every attribute added to it renumbers the handles of storage, diagnostics and mute, and a bonded phone holding a cached GATT database would address the wrong attributes until it re-paired (adding `0015`/`0016` there already cost one re-pair). Registered last, no existing handle moves, so **nothing that already worked can break or be misaddressed by a stale cache** — unlike a Settings characteristic, which would renumber those services. The new service itself is still absent from a cached database until the phone re-discovers (Service Changed, or the `gatt.refresh()` the app already performs when it fully closes a connection), so on Android the switch may not appear until the next clean reconnect. That is a missing control, not a broken device.
- **New (dev builds): The device records its own pairing state, so a silent bond loss is finally visible.** When an Omi silently loses its pairing, the phone can only see the aftermath, and the device had no way to report it: the existing "No persisted BT bond keys yet" log line goes nowhere without a wired debug probe (the serial console is compiled out). `transport_start` now emits a `DIAG_BOND_STATE` event carrying the number of bonds that actually loaded, and both deliberate wipe paths (the armed post-update unpair, and the 5-tap-and-hold gesture) emit one too. A boot reporting zero keys with no preceding wipe event is a silent loss; the same reading after a wipe event is expected. Costs one ring record per boot and nothing at runtime.
- **Fix: An Omi that has silently stopped recording now recovers on the next recording, unmute, or mode switch, instead of needing a reboot.** In auto mode the device sleeps between sounds and is woken by a hardware line from the microphone. If the mic wedges, that stops working in one of two ways — the line sticks on, so no further wake can ever register, or the mic stays powered but returns pure digital silence — and either way the Omi records nothing at all until it is restarted. Two things hid it. Stopping a Priority Recording is precisely the moment the device drops back into that sleep, and a button press wakes the device in software without ever consulting the mic, so every *manual* recording still appeared to work while automatic capture was dead. Observed as 14.5 hours with not a single byte written to the SD card, where every recording that did show up was traceable to a button press. The cure for both modes is the same — power-cycle the mic — and the Omi now does that at every point where you've signalled that recording should be working: starting or stopping a recording in either mode, unmuting, switching from Manual to Automatic in the app, and tapping a marker while nothing is being recorded. (A marker tapped *during* a recording deliberately doesn't, since a reset would punch a small hole in the audio exactly where the marker points.) **Muting and unmuting never actually reset the mic before**; it only stopped and restarted the receiving peripheral on the Omi, leaving a wedged mic untouched, which is why the obvious thing to try didn't help. Nothing is lost by the reset — the mic holds no settings the firmware writes, so it comes back exactly as it is after a reboot. There is deliberately no automatic background recovery: if this starts happening regularly it points at failing hardware, and silently papering over it would hide that.
- **New (dev builds): An on-device diagnostic event log (`CONFIG_OMI_DIAG_LOG`).** A small volatile RAM event ring records per-event timing + cause context for the health events the aggregate drop counters (`0x19B10062`) only total — empty-bin rotations, marker write drops, pause-gate saves, priority start/stop, session-end emits, and SD block / codec drops. Each record is 16 bytes (`seq`, uptime, code, backend, two args). It's drained over two new characteristics on the Diagnostics service — `0x19B10063` (read: snapshot header + packed records, GATT Long-Read-safe via an offset-stable snapshot) and `0x19B10064` (write: `[enable][ack_seq]`, ack-gated clear) — and advertises a capability bit (`1<<12`) so the app can gate its UI. The ring is **compiled out entirely in production** (zero code / zero RAM); in dev builds its 2 KB is reclaimed from the SD-writer stack, so it's RAM-neutral, and it's additionally gated OFF at runtime until a developer enables it. Enqueue is O(1), spinlock-guarded, and never touches the SD card, so it can't perturb the audio path it measures. Delete-on-connect is interruption-safe: records are only dropped after the app acks a successful read, and a keep-newest overflow (phone away too long) is counted, not silently lost.

### oo-2.7

- **New: A raw circular-log ("ring") audio storage backend that doesn't drop audio as the card fills.** The default flash filesystem (LittleFS) keeps no persistent free-space map, so once the card is full it runs a whole-card scan to allocate each new block — a pass that stalls the SD writer for seconds and drops audio, precisely in the all-day-offline state where the card stays full. The new backend writes recordings as an append-only circular log with an O(1) tail pointer: no free-space scan ever runs, so the write path holds steady throughput no matter how full the card is. Writes are batched into page-aligned 4 KB flushes (sub-page writes had forced the NAND into slow read-modify-write cycles) and the SPI bus is woken once per write burst instead of per block — together these took the SD write-queue from pegged-and-dropping to a small steady depth in testing, with zero dropped blocks across a full recording-plus-sync session. Durability: the backend never advances its committed head past bytes it hasn't flushed, so an unclean power-off loses at most the last in-flight block, and closed recordings are immutable. All ring metadata lives on the SD card (never internal flash), so a firmware update can't disturb it. **Opt-in and not the default** — see the selector below.
- **New: Runtime storage-backend selector (`CMD_SET_BACKEND`, `0x1A`).** The backend is chosen at mount from a persisted setting rather than fixed at build time, so it can be switched from the app and rolled back without reflashing. Switching saves the setting and cold-reboots; each backend reformats the card when it doesn't find its own layout. Safety nets: if the ring backend fails to mount it reverts to LittleFS (recording always resumes), and three consecutive boot failures auto-revert to LittleFS as well, so a bad ring state can't wedge recording. The default is LittleFS, so flashing this firmware changes nothing until you opt in. The storage read-control characteristic's status byte now also reports the mounted backend, so the app can show which one is live.
- **New: Ring-backend I/O diagnostics.** The SD-drop counter payload (`0x19B10062`) gains two fields (now 84 bytes): the slowest single SD operation since boot (tagged write / read / sync) and a count of write/sync I/O errors — so a write stall or a failing card is visible in Debug Tools without a debug cable. Older apps read the shorter prefix and ignore the new fields.
- **Change: Thread-stack rebalance (net-zero memory).** The SD-writer stack was trimmed — its format path no longer needs a large stack buffer — and the reclaimed space handed to the audio-codec stack, which had been running close to its ceiling. Overall memory use is unchanged; both stacks now sit comfortably within budget on either backend.
- **Fix: The ring backend drains the battery far less while recording.** The ring backend was committing its write cursor to flash far more often than it needed to — up to ~10× the filesystem's rate during continuous audio, again on every acoustic wake from silence, and (when the app was connected, i.e. open) on essentially every audio block — and each commit forces a power-hungry flash operation, so an Omi on the ring backend ran down noticeably faster than on the default filesystem. It now commits on the same ~1-minute cadence the filesystem uses, or after 256 KB of new audio (whichever comes first), and no longer forces an extra commit every time speech resumes after a silence — while still committing immediately at recording boundaries (Priority-Recording start/stop, manual stop, button and mute markers) so no start or stop is ever lost. On an unclean power-off — realistically only a flat battery for an offline device — at most the last ~1 minute of an in-progress recording's tail can be lost, which is imperceptible in practice. Ring backend only; the default filesystem is unchanged.
- **Fix: A firmware update no longer makes a needless write next to the Bluetooth bond keys, a suspected cause of an Omi coming back from an update unpaired.** Before every update the app clears the Omi's one-shot "wipe pairing after update" flag — on *every* update, including the common case where the "Reset pairing after update" option is off and the flag is already clear. The device stored that flag in the same internal memory that holds its Bluetooth bond keys and then rebooted to install the update seconds later; writing to that memory right before a power event is a plausible way for a neighbouring bond key to be left unreadable, so the device boots the new firmware unable to recognise the phone and won't reconnect until you Forget-Device and re-pair. The firmware now skips the write entirely whenever the flag isn't actually changing (the usual case), so an ordinary update never touches the bond storage; a real arm or disarm — including clearing a genuine stale flag from an earlier failed flash — still writes as before.
- **Fix: Switching storage backend now always reformats the card, so the Omi doesn't come back recording nothing.** Switching backends is meant to wipe the card to the target layout, but the switch only saved the setting and rebooted — the actual reformat happened only when boot didn't already find the target backend's layout on the card. After a round-trip (e.g. LittleFS → Ring while an older ring header still lingered under the LittleFS data), boot could mount that stale ring metadata: it passed the mount check but pointed at bytes LittleFS had since overwritten, so the device captured and listed nothing while every drop counter read zero. The switch now records which backend to format and applies it on the next boot — a genuinely clean target layout every time — validated against the backend actually being mounted, applied only on the boot mount (never a mid-session remount), and kept armed until the format commits. So an ordinary reboot never re-wipes, a switch that's interrupted or whose save fails leaves the current card untouched rather than half-applied, and a reset mid-format simply re-formats on the next boot instead of mounting stale data. The app already warns that switching erases the card, so sync everything off first.

### oo-2.6

- **Fix: Fewer dropped audio blocks during long recording sessions.** To find free space, the flash filesystem periodically scans the whole card — a pass that briefly stalls SD-card writes and, on a fuller card, can run for several seconds. If it landed in the middle of recording, the write queue could back up and drop audio. The firmware now scans the card about half as often (larger free-space lookahead window) and carries more write-queue headroom (100 → 120 blocks) to ride out the scans that still happen. Keeping the card emptier (syncing regularly) keeps each scan short, since the scan's length grows with how much is stored. New diagnostics in Debug Tools show "SD worker stack" / "Codec stack" peak usage to gauge reclaimable device memory. Requires firmware ≥ `oo-2.6.2`.
- **New: Live diagnostics + charging notifications during a sync.** The SD-write drop-counter characteristic (`0x19B10062`) is now READ **and** NOTIFY: while the app is subscribed the firmware pushes the 76-byte counter payload on a timer — every 2 s during an active file transfer (when the write queue builds and drops occur), with a slow 15 s heartbeat otherwise — so the app's diagnostics view updates live during a sync instead of going dark, without the app having to issue a GATT read that would race the storage notify stream. The 2 s cadence now engages the moment a transfer becomes active (a cross-module kick from the storage thread) instead of waiting out the current 15 s idle interval, so the live view doesn't lag the sync start by up to 15 s (firmware ≥ `oo-2.6.3`). Emits only while a client is subscribed, and stops on unsubscribe/disconnect. The battery charging-state notification (`0x19B10051`) is likewise no longer skipped during a transfer; it's a one-byte notification on the existing battery-refresh cadence (~60 s while connected, plus once on subscribe), and the storage stream's existing retry/yield absorbs the momentary TX-buffer contention.
- **New: Remote reboot and power-off commands.** Two new storage-protocol commands, both deferred to the storage thread so the device ACKs the app *before* the link drops. `0x16` cold-reboots the device (`sys_reboot`), which then restarts and re-advertises for the phone to reconnect. `0x17` powers the device fully off via the existing graceful shutdown (`turnoff_all()` → `sys_poweroff()`) — ship mode, waking only on a button press or charger. Surfaced in the app as Device Settings → "Reboot Omi" / "Shutdown Omi". An in-progress recording's last unwritten block may be lost, the same as any unclean stop.
- **New: One-shot "unpair after firmware update" marker.** A new command (`0x18`) records the current firmware version in persistent storage; on the next boot the device wipes all BLE bonds and advertises unbonded so the phone re-pairs cleanly — but **only when the running version differs** from the one captured at arm time (i.e. an update actually landed). A failed or aborted flash leaves the same version, so it never wipes your pairing on a later ordinary reboot; only a genuine update does. Capturing the version when you arm (before the flash) also makes it fail-closed: if arming doesn't persist, nothing wipes. The app arms it before a flash when you enable "Reset pairing after update," and disarms it otherwise.

### oo-2.4

- **New "Start Recording" / "Stop Recording" button actions for guaranteed (Priority) recordings.** Two new mappable button actions. In automatic mode, Start rotates the SD bin, writes a priority-start marker (`0xFFFFFFF8`), and forces continuous capture (VAD threshold 65535) so nothing is dropped to silence; Stop restores the auto threshold — which emits the existing session-end marker (`0xFFFFFFFC`) — then rotates again so the recording owns whole bins. A safety cap auto-stops a Priority Recording left running too long (default 2 h) so a forgotten recording can't drain the battery or fill the card. In manual mode the same actions are explicit start/stop (persisted across reboot, like the existing button toggle). Mode is read from the persisted threshold so a marker/mute tap during a Priority Recording behaves correctly instead of misreading the forced 65535 as manual mode.
- **Switching to Manual Mode mid-recording now ends the current auto recording cleanly.** Lowering the VAD threshold into manual standby (`32769`) while a recording is active now emits a session-end marker immediately, instead of letting ~10 s of post-switch audio leak into the recording via the silence-hold tail.
- **The Marker button action is no longer overloaded.** Previously, in manual mode the Marker action doubled as a start/stop recording toggle. With the explicit Record Start / Record Stop actions above, Marker now always just drops a bookmark in any mode — so you can mark a moment *during* a manual recording. The factory-default button mapping moved to single-hold = Marker, double-tap = Start, double-hold = Toggle LED, triple-tap = Stop (the app pushes a per-mode mapping on connect, so this only affects a device that has never been connected to the app).
- **Button actions can now play a vibration pattern.** A new per-gesture haptic setting lets each button action confirm itself with a short buzz — single, double, or triple (100 ms pulses, 100 ms gaps) — configurable from the app over a new BLE characteristic (`23ba7928`, in the existing button-config service). The motor driver was reworked into a single non-blocking pulse-train sequencer that owns the motor end-to-end, so a button pattern can't collide with the existing power-off / unpair / boot buzzes. The buzz fires only when the action takes effect (a manual-mode mute no-op stays silent). Defaults to off for every gesture.
- **Manual-mode recording now survives a reboot.** When you start or stop recording with the device button in manual mode, that state is now saved to flash. Previously it was only held in memory, so if the device rebooted (e.g. the battery drained) while you were recording, it came back up in standby and silently stopped — and a deliberate stop could likewise be forgotten. Now a button start resumes recording after a reboot, and a button stop stays stopped. (Auto mode and mute are unaffected — mute is intentionally cleared by a reboot.)

### oo-2.3

- **Mute now lights the LED so you get confirmation.** Tapping mute turns the indicator solid red even when the LED is in its default off (stealth) state, so you get clear feedback that the mic is muted — previously a mute tap showed nothing unless you'd separately enabled the LED. Unmuting returns the LED to whatever it was before (off stays off). If you'd rather keep it dark, you can still toggle the LED off while muted; the next unmute restores your pre-mute state. (Auto mode only — manual mode has no mute.)
- **Faster sync on iOS via an Apple-compatible connection-interval fallback.** The device requests an aggressive 7.5 ms Bluetooth connection interval for fast SD-card sync, but iOS rejects any request below 15 ms outright and silently leaves the link at its slow default (~30 ms), so iPhone sync crawled. The firmware now rechecks the *actual* negotiated interval a few seconds after connect and, only if its fast request wasn't honored (i.e. an iPhone), sends a single Apple-compliant request (15–30 ms). Android is unaffected — its phone already drives the interval to ~11 ms via a high-priority request, so the recheck sees a fast interval and does nothing. The fallback self-targets iOS by observing what the central accepted rather than detecting the OS, and is sent at most once per connection so it can never loop. Pairs with the iOS app changes in 0.25.

### oo-2.2

- **Fix: No more mid-transfer disconnect loop on slow links (notably iOS).** During an SD-card transfer the device keeps the BLE link up even when the phone drains data slowly. Previously a slow consumer could back-pressure the firmware's send path so no data flowed for >15 s, tripping the idle-disconnect that exists to save power when truly idle — which cut the transfer off, and the resumed transfer cut off again, looping. The idle-disconnect is now deferred while a transfer is in progress (the BLE supervision timeout still drops a genuinely dead link). This mainly affected iOS, where the file read runs packet-by-packet on the phone instead of in native code.
- **New: Clean slate when flashing over non-Omi-offline firmware.** The first boot after flashing onto a device that was running a different (e.g. stock Omi) firmware wipes the SD card storage so old, incompatible recordings don't linger. The trigger is the on-card filesystem itself — the NAND is reformatted whenever it isn't recognized as an Omi-offline filesystem (every Omi-offline format stamps a magic cookie) — so this runs exactly once on migration. **Bluetooth bonds are left intact**: the pairing key stays valid across the firmware swap, so your phone reconnects without re-pairing (iOS in particular has no API for an app to clear a system pairing, so wiping only the device side would have forced a manual "Forget This Device"). Use the 5-tap-and-hold unpair gesture or Forget Device if you deliberately want a fresh pairing. Upgrading between Omi-offline versions keeps the cookie and therefore **never** wipes storage (unlike the old per-version wipe removed in oo-1.9).
- **New: Customizable button finite state machine.** Replaced the static button click logic with a counter-based state machine that resolves each tap-count + hold against the custom mapping synced from the app over a new **encrypted, value-validated** BLE service. 4-tap and 5-tap holds are hardware-enforced for Power Off and Unpair and cannot be overridden by a custom mapping; over-tapping past 5 is a harmless no-op.

### oo-2.1

- **Security: GATT encryption lockdown.** All sensitive and writable characteristics — offline storage, device settings, time sync, haptics, mute, and the accelerometer CCCD — require mandatory encryption (pairing), so an unauthorized device in range can't download recordings, mute the mic, or alter settings. `CONFIG_BT_KEYS_OVERWRITE_OLDEST` and unauthenticated-overwrite are removed, so the Omi won't let any unauthenticated device overwrite your existing bond slot — it accepts only the legitimately bonded phone, or a new phone after a physical unpair gesture. Core recording infrastructure (the SD writer thread and audio pipelines) is left untouched.

The app can trigger the same wipe with `CMD_UNPAIR` (`0x15`) on the storage characteristic, which calls `bt_unpair()` and drops the connection for synchronized unpairing.

### oo-2.0

- **New: mute markers in the audio stream.** Engaging/releasing mute writes a mute-on (`0xFFFFFFFA`) / mute-off (`0xFFFFFFF9`) marker into the recording stream (same 16-byte payload as the other markers: UTC ms, uptime ms, session id), so the app can reconstruct exactly when the mic was muted. SD writes are resumed before the marker is written, so it survives even if mute was toggled during a VAD silence gap; the markers are force-drained like button-tap/session-end markers so they're durable with no audio flowing.

### oo-1.9

- **New: `0x32` keep-alive command** resets the idle-disconnect timer — now **15 s** (shortened from 30 s) — to prevent disconnects during long file reads; the device falls back to low-power advertising when idle.
- **New: mute state exposed over BLE.** A Mute service (`0x19B10070` / characteristic `0x19B10071`, Read/Write/Notify) reports whether the mic is muted plus when mute was engaged (`[muted][since_utc_s][since_uptime_ms]`); writing `0`/`1` toggles mute (honored only in auto mode, mirroring the physical-button gate). Notifications fire on subscribe and on every change and are intentionally **not** suppressed during file sync. The characteristic is registered last so all existing handles stay stable.
- **Diagnostics characteristic (`0x19B10062`), now 40 bytes.** Exposes reset cause + uptime and SD/codec/BLE drop counters, plus failed-connection count, SD-queue peak depth, and write-fairness activation count. Older apps read the prefix.
- **Reliability: write fairness.** The SD worker forces a write turn after a run of consecutive file reads, so an active BLE sync (file reads) can't starve audio writes; transient write stalls during connect/sync no longer drop audio immediately (retry window relaxed to 25 ms). The SD request queue holds 100 slots and the codec ring buffer is 1.0 s (up from 0.6 s) for more headroom against codec-thread stalls.
- **Reliability: durable in-stream markers.** Button-tap (`0xFFFFFFFE`), session-end (`0xFFFFFFFC`), and VAD-resume (`0xFFFFFFFD`) markers use a blocking SD write so they aren't dropped when the write queue is briefly saturated; audio ordering is preserved.
- **Reliability: SD recovery and bounded boot.** If writes fail repeatedly mid-recording, the firmware power-cycles and remounts the card instead of dropping audio until the next reboot. If the SD card fails to initialize within 90 s, the device still comes up (BLE + mic) and **blinks** the LED red so the fault is visible (and distinguishable from the solid-red mute indicator) instead of hanging on boot.
- **Battery: idle power saving is SPI-bus suspend only** — the card stays mounted and powered, and the NAND only fully powers off at shutdown. (An earlier deep power-gate that fully powered the NAND off during long silence was reverted: a failed wake-remount could latch the write path and silently drop all audio until a manual reboot.) Recording continues down to the critical-voltage clean shutdown, with one durable flush at the low-battery threshold, instead of pausing at 15% battery.
- **Removed: the SD-card wipe on firmware version change** — booting a new firmware version no longer reformats the SD card, so unsynced recordings survive an OTA/flash.
- **LED: defaults to off after the boot sequence** (the initialization flash still plays on every boot); charging restores the previous LED state on unplug (stealth stays stealth, LED-on stays LED-on).
