## Architecture

### Overview

Omi is an offline-first wearable audio recorder. The nRF5340 firmware captures audio via Opus codec, stores it to SD card, and exposes it over BLE. The Flutter app discovers the device, syncs recordings via WAL, decodes Opus to .m4a, and splits by silence.

**Data flow:** Mic → Opus encode (firmware) → SD card → BLE transfer (WAL-tracked, ACK-gated, resumable) → raw .bin segments on phone → Opus decode → VAD silence detection → .m4a → daily batch UI → *(opt-in only)* integration upload

Everything up to the daily batch UI happens with no network at all. The one path off the device is the opt-in integration upload — see **Integration uploads** below.

**One Omi at a time.** The app is built for exactly one paired, connected Omi — a product decision, not a platform guarantee (the BLE stack and the WAL layer are both capable of more). Treat a "device switch" mid-session as out of scope rather than impossible. Do **not** add per-device scoping (device-id-suffixed preference keys, cached state keyed by device, teardown-on-device-change branches): it is untestable, it is cost with no return, and reviewers repeatedly flag its absence as a bug. Where cached device state exists (diagnostics counters, the diag-log ring, capability bits), say in a comment that the omission is deliberate. Keying by device id purely so a *replacement* unit re-runs one-time setup is fine — that is a different thing from supporting two devices.

### App (`app/lib/`)

**State management**: two `ChangeNotifier`s drive the UI. `DeviceProvider` owns device discovery/connection/battery/mute state. `RecordingsController` (`pages/recordings/recordings_controller.dart`) owns the recordings page: it runs the sync→process pipeline state machine (`SyncProcessState`: idle/syncing/processing/stopping/resume/error/successUi, with a stall watchdog that force-recovers wedged BLE transfers), builds the daily `Batch` / `MarkerConversation` UI models from `RecordingsManager`, handles deletion + discard recovery, and delegates external-integration uploads to `IntegrationUploadManager` (`integration_upload_manager.dart`, with `passthrough_integration.dart`). `ServiceManager` is the singleton that holds `IDeviceService` and `IWalService`. (`pages/settings/sync_page.dart` is the **Debug Tools** screen — manual sync/process drive, diagnostics counters, the event log — not part of the recordings page.)

**Android process lifecycle** (`android/.../MyApp.kt`, `MainActivity.kt`, `main.dart`): the `FlutterEngine` is created and cached by the **`Application`**, not the Activity — `MainActivity` adopts it by id and sets `shouldDestroyEngineWithHost = false`. Android reclaims a backgrounded Activity routinely, and `OmiBleForegroundService` keeps the process alive regardless, so an Activity-owned engine meant the BLE layer kept running with **no Dart at all**: every sync path is Dart-side, so both wake paths took their "engine not running" branch and returned success having done nothing (17 h observed on-device 2026-08-28; 68 files drained on next app open). Invariants:
- **`cleanUpFlutterEngine` must not null `flutterApi` or clear `isFlutterAlive`.** The engine is not going away; saying otherwise tells both wake paths Dart is dead while it runs fine, which is the original bug. It releases only the Activity reference and the companion manager.
- **Exactly one engine.** A headless per-sync engine would race the Activity's over the BLE stack.
- **`DeviceProvider` is constructed in `main()`, not by the widget tree.** Its constructor registers `BleBridge.backgroundSyncRequestedCallback` — the entry point for every scheduled sync. A WorkManager-started process may never attach an Activity, and with no view nothing drives a frame, so a lazy `ChangeNotifierProvider` may never build it; native would report Dart alive and `BleBridge` would call a null callback.
- **Readiness is `dartReady`, never engine construction.** `executeDartEntrypoint` only *schedules* `main()`, so a flag set at construction promises a Pigeon handler that does not exist yet. Dart signals over the system channel once the sync path is up; a `main()` that throws correctly leaves the flag false.
- **Foreground is native's `hasUi`, never a null `lifecycleState`.** Null used to mean "just launched, assume foreground" — safe only while a widget tree (i.e. a screen) was the sole builder. Headless, the null never resolves and the app holds the link open believing someone is watching. Do not flip the default instead: a genuine cold start is also briefly null. `lifecycleState` still wins when set.
- **Nothing in `main()` may require an Activity.** `permission_handler` throws without one, so permissions are requested only after `hasUi` says yes. The AAC encoder is engine-scoped for the same reason — Activity-scoped, background processing got `MissingPluginException` and silently fell back to WAV. `main()` now runs once per *process*, so launch housekeeping re-runs on each UI attach (idempotent, 10 s debounce), and native signals **every** attach, not only re-attaches.

**Background sync scheduling** (`device_provider.dart`, `BackgroundSyncWorker.kt`, `SyncAlarmReceiver.kt`): three triggers — the Dart interval timer, a native `AlarmManager` exact alarm, and a WorkManager backstop — and **all three anchor on `lastSyncCompletedMs`**. The pref's setter carries the completion signal; do not hook the three call sites instead, because the sync that completes is not always the one the scheduler started (`RecordingsController` runs the foreground pipeline and holds no `DeviceProvider`). `_anchorAutoSyncSchedule()` is the single writer for the timer phase, and `_publishNextSyncTime()` the single writer for the two pushed consumers (UI + exact alarm) — every site that ends a cycle, `_failSyncCycleToIdle` included, goes through them, or the triggers drift apart. WorkManager's period is a **floor** (15 min minimum, fired inexactly), not a schedule of its own, so it gates on the same pref *and* on `lastSyncSkipped` the way Dart's `_shouldSyncNow()` does. A skip deliberately leaves `lastSyncCompletedMs` alone — nothing was pulled — so it must not push the schedule out. **That applies to the throw path too**, which is easy to miss because it is a separate branch: `_doBackgroundSync`'s inner `catch` used to stamp a completion, and a `DeviceConnectionException` from a link that died during connect-setup is the most common thing it catches. Stamping there cost twice over — it pushed all three triggers out a full interval, and by clearing `lastSyncSkipped` it disarmed `_shouldSyncNow()`, which is the only reason `_handleDeviceConnected` adopts a link native hands back seconds later (observed 2026-08-31: six files waited an hour after a five-second glitch that had already recovered). The catch records a skip and re-anchors, and only `lastSyncStatusMs` — the display clock, which is what the notification reads — is stamped. Nothing may write `lastSyncCompletedMs` unless the device was actually reached and the run finished.

Two further writers record a skip for a cycle that produced **no outcome at all**, which the three triggers above cannot do for themselves. `SyncAlarmReceiver` (native) records one when the alarm fires and Dart is not up (`flutterApi == null`, i.e. `dartReady` never arrived in this process) — every sync path is Dart-side, so that cycle demonstrably pulled nothing; it writes from a branch where no live isolate can race the pref file. `DeviceProvider._sweepOrphanedSyncCycle()` (Dart) covers the other half: `syncCycleStartedMs` is stamped when a cycle is accepted and cleared on every terminal path, so a non-zero value found by a **fresh process** belongs to a cycle whose owner is gone and can never finish. Both write `lastSyncSkipped` + `lastSyncStatusMs` only, never `lastSyncCompletedMs`. Neither can see a cycle merely **frozen** — a freeze is not a death and nothing distinguishes them; that one resolves on thaw. Do not replace either with "did `lastSyncStatusMs` advance since the last alarm?", which cannot tell a dead cycle from a sync legitimately outrunning one interval and would write "Skipped" over a sync in progress. See NOTES.md, "Recording a cycle that could not run".

**Connection pipeline** (`services/devices/`, plus `services/devices.dart` and `services/devices/discovery/` — the `DeviceService`/`Mutex` owner is the top-level `devices.dart`, not a file inside the folder):
- **GATT-cache refresh (Android)**: Android persists a bonded device's attribute database and answers discovery from it, so a firmware flash that adds/moves attributes leaves a stale map (new services invisible; shifted handles misaddressed). `DeviceProvider._gattCacheRefreshFingerprint` fingerprints the device as `<DIS firmware revision>|<capability bitfield>` (`gattFingerprint_<deviceId>` pref) and returns the new value when it changed; `_onDeviceConnected` persists it **and** calls `recycleConnection()` together, **after** clearing `_currentlySettingUpId` (recycling re-enters `_onDeviceConnected`, which would early-return and leave the new link unconfigured). The reconnect path already calls `closeGatt()` → `BluetoothGatt.refresh()`, so no native change is needed. Invariants worth preserving:
  - Both halves of the fingerprint matter: version alone misses a dev↔production swap at the same version, which differ in attribute count via `CONFIG_OMI_DIAG_LOG`.
  - The capability read uses `getFeaturesIfIdle()`, never `getFeatures()` — this runs on a link a sync may be using, and an unserialized read there drops the link on Android.
  - Persist happens **after** `recycleConnection()` returns true, not at evaluation: the `isSyncing` re-check immediately before recycling can skip it (a sync can start after evaluation — setup kicks one off unawaited), and `recycleConnection()` itself no-ops when one is already in flight or the link dropped. A refresh that never ran must leave nothing behind that suppresses the retry on the next connect — hence `recycleConnection()` returning whether it actually started.
  - There must be **no `await` between the `isSyncing` check and the `recycleConnection()` call**. Dart's single thread makes that pair atomic only while it contains no suspension point; adding one (an awaited persist, a log flush) reopens the window for a sync to start after the check.
  - First sighting of a device refreshes **once, per device** — never gated on a global one-shot, because a pre-fingerprinting device may already hold a stale cache. The `gattFingerprint_<deviceId>` key is keyed by device id only so re-pairing a replacement unit still gets its refresh; it is not there to support two Omis at once (see **One Omi at a time** above). The price of not being able to tell "predates fingerprinting" from "freshly paired" is one wasted reconnect, once.
  - Skipped entirely on iOS (no `refresh()`; relies on Service Changed) and on a `features == 0` read (degraded link).
- `DeviceService.ensureConnection()` is serialized via a `Mutex` (`devices.dart`) — N concurrent callers (battery, storage, WAL sync) share one connection attempt. Critical: never bypass this.
- Connection retry and reconnect logic is owned by the native BLE layer, not Dart. When the transport exists but is disconnected, do not dispose and recreate it — that cancels native's auto-reconnect.
- `OmiDeviceConnection` has its own `_storageMutex` covering CMD_LIST_FILES / CMD_READ_FILE / CMD_DELETE_FILE so storage commands serialize against each other even when sharing the same connection.
- On connect: time sync writes UTC as little-endian u32 to `timeSyncWriteCharacteristicUuid` so the device can anchor recording timestamps.
- Foreground sends a periodic keep-alive (`0x32` to `storageDataStreamCharacteristicUuid`) to keep the firmware from idle-disconnecting. Dead connections are force-dropped after consecutive keep-alive failures.

**Audio pipeline** (`services/`):
- `SDCardWalSyncImpl` saves downloaded segments to `raw_segments/<timerStart>/<timerStart>_<sessionId>.bin`, where `<timerStart>` is the firmware-assigned UTC epoch seconds (as a decimal string). Pre-time-sync files (timerStart < 946684800) land in `raw_segments/session_<sessionId>/` instead and appear in the UI under "Unorganized". Inline-frame types in the bin stream:
  - `0xFFFFFFFB` metadata header (36 B: 4-byte tag + 4-byte length + 28-byte payload), peeked at offset 0
  - `0xFFFFFFFC` session-end marker (20 B): 4-byte header + same 16-byte payload as the button-tap marker; written by firmware on manual-mode stop
  - `0xFFFFFFFD` VAD-resume timestamp (20 B): 4-byte header + 16-byte payload `utc_s(u32) + uptime_ms(u32) + 8 zero bytes`, written when AAD wakes after silence. **Payload layout differs from the other markers**: UTC is epoch *seconds* (u32), not ms (u64), and there is no session id.
  - `0xFFFFFFFE` button-tap marker (20 B): 4-byte header + 16-byte payload of `utc_ms(u64) + uptime_ms(u32) + session_id(u32)`
  - `0xFFFFFFFA` / `0xFFFFFFF9` mute-on / mute-off markers (20 B each): 4-byte header + same 16-byte payload as the button-tap marker; bracket a muted stretch in the stream (rendered as a "muted" ghost row)
  - `0xFFFFFFF8` priority-recording start marker (20 B): 4-byte header + same 16-byte payload as the button-tap marker; written by firmware on an auto-mode RECORD_START (after rotating the bin). The app finalizes the current auto recording at this boundary and opens a high-priority ("Priority Recording") recording rendered red, force-captured (no silence split) until the matching `0xFFFFFFFC` stop. **This is the only marker that finalizes mid-stream and keeps consuming into a new recording**, which is why the firmware rotates the bin around it (recording boundary = bin boundary; avoids whole-bin re-VAD duplication).
  - `0xFFFFFFFF` / `0`: sentinel slots — standalone padding words, ~10% of a real bin
  Anything else is an **audio frame**: a 4-byte little-endian payload length, the VBR Opus payload, then padding to the next 4-byte boundary (so the stride is `4 + ((len + 3) & ~3)`, not `4 + len`). Dropping that alignment desyncs the walk at the first frame — `real_bin_format_test.dart` pins it against real firmware bytes.
  These frames are left inline in the bin file — not extracted at transfer time. `VadAudioProcessor` parses them during the decode pass.
- `VadAudioProcessor` decodes Opus → 16 kHz mono 16-bit PCM (`opus_dart`) and runs Silero v5+ VAD (`flutter_onnxruntime`, model `assets/models/silero_vad.onnx`; 512-sample windows, 64-sample context, persistent LSTM state reset on gap) to detect speech, splitting into `recordings/<YYYY-MM-DD>/recording_<millis>.m4a`. It also writes the `.meta` sidecar.
- `VadAudioProcessor` emits an EDL sidecar `recordings/<YYYY-MM-DD>/marker_<markerMs>.edl` (JSON: `markerTimestampMs`, `segmentFilename`, `markerOffsetMs`, `cropStartMs`, `cropEndMs`, `userSaved`) per detected button-tap. Markers with no surrounding audio are emitted as orphan EDLs with an empty `segmentFilename`. Markers re-anchored across stitched files have their offsets shifted by the prefix's wall-clock duration.
- `RecordingsManager` / `Conversation` model parses finalized recordings from the `recordings/` directory for UI binding; `RecordingsManager.getMarkerConversations()` builds the `MarkerConversation` list from the EDL sidecars.

**VAD processing design invariants** (`services/vad_audio_processor.dart`, `services/recordings_manager.dart`):
- The firmware writes sequential bin files, rotating at `FILE_ROTATION_INTERVAL_MS` = **10 minutes** (`sd_card.h`). Explicit rotations — app command, BLE connect, priority start/stop, manual stop — make real files shorter than that. Each file's `segmentStartTime` (the WAL `timerStart`) picks up exactly where the previous file ended — no overlaps, no gaps larger than clock drift.
- **The active bin is not listed.** `CMD_LIST_FILES` omits the file currently being written, so a recording is only fetchable once something rotates it. Both implicit rotations (age, BLE-connect) are evaluated in `should_rotate_file()`, which is called **only from the write path** — so a device that has stopped writing never rotates on its own. That stranded every manual recording's last bin, the one holding its own `0xFFFFFFFC`, until the user recorded again or hit Force Sync (confirmed on-device 2026-08-16: stop at 03:47, five background syncs told "0 files", released 2h33m later by a manual Force Sync). Two things close that hole and both must stay: `record_stop()` (`button.c`) rotates on a manual stop exactly as `priority_record_stop()` always has, and the `REQ_FLUSH_FILE` handler (`sd_card.c`) services the pending BLE-connect rotate — that request is posted on every connect and does not depend on the mic, so it is the only place that runs while idle. The button-side rotate is deliberately **not** in `aad_set_threshold()`: the app's own threshold writes reach it on the BLE callback thread, where a blocking SD wait stalls the stack into an ATT timeout. App-driven stops are covered by the idle-connect rotate instead.
- The processor treats all bin files as one continuous audio stream. A recording starts when speech is detected and ends only on: (a) `vadSplitSeconds` of continuous silence (auto-mode default 120 s; manual mode forces 0 / VAD-off), or (b) the `vadMaxConversationMinutes` cap (`0` = no cap). **The processor reads the flat `vad*` prefs, never the mode label** — `manualMode` is only a label. `applyRecordingModeDefaults()` (`preferences.dart`) is the single writer that keeps them in step: manual pins `vadEnabled=false` / `vadSplitSeconds=0` / `vadMinSpeechSeconds=0` and takes the cap from `manual_vadMaxConversationMinutes`; auto restores its own snapshot (`auto_vadEnabled`, `auto_vadSplitSeconds` (120), `auto_vadMaxConversationMinutes`, …). Both per-mode caps default to `0`; the flat `vadMaxConversationMinutes` still carries the pre-per-mode default of 60 for a user who has never switched modes. Letting the label and the flat prefs disagree is a real, shipped failure — an auto label sitting over manual's `vadSplitSeconds = 0` is the 2026-08-14 configuration. Nothing else creates a boundary.
- There is no separate `vadGapSeconds` constant. The gap threshold between consecutive files is `vadSplitSeconds - _firmwareVadHoldMs` (10 s). With the default `vadSplitSeconds` of 120 s, file gaps up to 110 s are stitched. BLE disconnects do not create file gaps — firmware writes straight to SD card regardless of phone connectivity.
- Manual mode is the default since 0.14.0 (`manualMode` preference defaults to `true`). In manual mode the app writes `vadThreshold=65535` (VAD off, recording on) on start-tap and `32769` on stop-tap; the firmware emits `0xFFFFFFFC` on stop so the processor can auto-finalize without Force Process.
- **End-of-run always flushes as a `_draft` file**, in both background and foreground modes. Recordings in progress are written via `flushRemaining(isDraft: true)`; the resulting `_draft.*` files are not surfaced as finalized recordings and are re-stitched with newly downloaded bins on the next sync+process cycle, then promoted to finalized recordings once silence/cap conditions are met. Do not change `isDraft: true` to `false` in the background path — that would prematurely promote partials and delete their source bin files, anchoring the next run's recordings to a too-early timestamp.
- The `VadAudioProcessor` is stateless across runs (recreated in a fresh isolate each time). Persistence is implicit: `_draft` files plus uncut bin files stay on disk and are re-processed.
- **The segment list's order IS the audio's order**, because the processor reads it as one continuous stream. Two things guard it and both must stay. `allSegments` sorts **numerically** on the parsed `timerStart`, never lexicographically on the basename: a pre-time-sync bin keys on uptime seconds, so `999_<sid>.bin` string-sorts *after* `1787709128_<sid>.bin` and lands a session's oldest audio at the newest end. And `RecordingsManager.shiftedResumeIndex` (pure, unit-tested) decides where a resumed run picks up: a bin is skippable only if it is **both** older than the checkpoint **and** was in the list that checkpoint covered. Timestamp alone is not enough — a bin can arrive *after* the checkpoint was written and still be older (a retried transfer, a short listing delivered next sync), and skipping it both strands its audio and splits the stream, since the tail gets finalized and its bins pruned before the older half is ever decoded, leaving the two halves unstitchable across a bogus multi-hour gap. Confirmed on-device 2026-08-26: a run resumed at 24/48 on the old rule, the next run re-decoded 19 of those 24, and the one bin the checkpoint had *named* lost its ten minutes for good. The rule stops new false claims being created but cannot recognise one already on disk — a poisoned checkpoint lists the skipped bins in `paths` exactly as an honest one does — so `checkpointVersion` (`recordings_isolate_worker.dart`) gates the file: a checkpoint not carrying the current version is discarded unread. Bump it for any change that alters what a checkpoint's fields *mean*, never for one that only adds a field.
- **`_currentStartUptime` must move with `_recordingStartTime`, at every site that opens a recording** — the per-frame `??=` anchor, both marker starts, the marker recalibration, the VAD resume, and the max-duration cut; `_resetState` clears it alongside. It is the `.meta`'s byte-412 value and the *only* thing `DeviceClockAnchor.startMsFor` has to place a recording by. Assigned only at bin entry (as it was originally), every mid-bin recording carries the head-of-bin uptime of whichever bin the stream was last empty at — which `clockVerdict` reads as the Omi's clock being minutes-to-hours wrong, since `plausibleDriftMs` is only the session length in ppm. The re-file that follows is not cosmetic: `promoteSessionToDate` renames to `uptime * 1000 + offset`, so every recording sharing a stale uptime derives the **same filename** and `File.rename` silently overwrites. The running `_currentFrameUptimeMs` is separately re-anchored to the bin header when a recording spans a bin boundary — it advances only per decoded frame, so each padded inter-file gap leaves it that much behind the device and the error accumulates. **The two sites inside `_applyVadVerdict` take the uptime as a parameter and must never read `_currentFrameUptimeMs` directly**: that method is also the Pass-2 replay body on the batched path (`_useBatchRunner`, i.e. Android with Silero — the production path), which runs after a whole batch of up to 6000 frames / 120 s has been ingested, so the running counter is already at the batch END. Reading it there gave every recording opened during one replay the same batch-end uptime, up to 120 s late — over the 60 s `plausibleDriftMs` floor, so the anchor re-filed a correct session, and identical across the batch, which manufactures exactly the shared-uptime collision `promoteSessionToDate` guards against. `_DeferredFrame.uptimeMs` carries it beside `frameTime` for the same reason `frameTime` is carried; `vad_batch_path_test.dart` drives both paths over one bin and asserts they agree.
- **`promoteSessionToDate` must never destroy a recording.** It moves *every* recording with the session's id — including ones `clockVerdict` judged `unplaceable` — so it cannot assume the targets are distinct. It skips `_draft.` files (renaming one strips the suffix, promoting a partial and stranding its tail) and refuses any target already claimed this pass or already on disk, leaving that recording under the timestamp the Omi gave it. A recording under a wrong date is recoverable; one renamed onto another is not. **The claim order is a sort, not `Directory.list()`** — earliest recording first, tie-broken on path. A refusal has a winner and a loser, so readdir order meant the same data could leave a *different* recording holding the wrong date on a different phone, with nothing to point at when a user asks why. Earliest wins because that is the recording `applyClockAnchors` anchors the whole session's offset on. Do not drop the sort as cosmetic: `recordings_manager_test.dart`'s shared-uptime test is order-dependent without it and had never passed.

**Sync** (`services/wals/`; `WalFileManager` lives in `utils/wal_file_manager.dart`):
- `WalService` creates `Wal` entries per file. A `Wal` carries exactly what the sync needs and nothing else: `device`, `fileNum`, `walOffset`, `storageTotalBytes`, `timerStart`, `sessionId`, `storage`, `status` (miss → syncing → synced), `isSyncing`, `syncFailCount`, `syncStartedAt`. **Do not re-add "placeholder" fields.** It used to carry `codec`, `channel`, `seconds`, `estimatedSegments`, `filePath`, `data`, `sampleRate`, `deviceModel`, `syncEtaSeconds`, `syncSpeedKBps` and `syncMethod` — a block the file itself labelled "Placeholder fields for compatibility with existing UI/Utils" — inherited from upstream, where a WAL was a chunk of *streamed* BLE audio. Every one was proved unreferenced by deleting it and finding `dart analyze lib` clean; `copyWith`, `getFilePath()`, the `SyncMethod` enum, `WalStatus.corrupted` and four top-level constants (`newFrameSize`, `segmentDurationSeconds`, `flushIntervalInSeconds`, `sdcardSegmentDurationSecs`) went with them. `wals.json` is rewritten by every sync, so dropping keys costs nothing: `fromJson` ignores what older files still carry, and a `status` of `corrupted` from an ancient file now falls back to `miss`, which re-downloads — the correct outcome anyway.
- `SDCardWalSyncImpl` reads files over BLE — allows resume on reconnect without re-downloading
- `WalFileManager.saveWals` / `loadWals` are serialized via a `Mutex` so a concurrent `saveWals` can't observe the file mid-truncate, read it as empty, and drop the WALs already written. (The original rationale cited a multi-device sync; the race is the same with one device, since several call paths persist WALs concurrently.)
- During fast-path sync, `onProgress` fires per BLE packet (~50 Hz). Persist calls are throttled to ~1 Hz; state-transition saves (deletion, transfer failure, end-of-sync) still persist immediately. The truncate-on-resume guard at the start of `_readStorageBytesToFileLocked` bounds re-fetch on crash to one persist-window of bytes.

**Integration uploads** (`pages/recordings/passthrough_integration.dart`, `integration_upload_manager.dart`, `models/integration_upload_types.dart`, `services/omi_api_client.dart`, `services/heypocket_service.dart`; UI in `integration_status_section.dart` + `pages/settings/integrations_page.dart`):

This is **the only path that sends recorded audio to a server on its own** — unattended, on a background sweep — so it is off by default (`heypocketEnabled` / `omiSyncEnabled` both default false) and stays off until the user configures one. "Offline-first" is a claim about the default and about the capture/sync path, not about the whole app. (The OS share sheet in `recordings_page.dart` / `recording_player_page.dart` also hands audio out, but only per explicit tap and to whatever the user picks; it is not an upload path and has none of the machinery below.)

- Two `PassthroughIntegration` implementations, both listed by `getIntegrations()` — **HeyPocket** (single-shot; uploads the finalized **audio file**) and **Omi Cloud** (chunked; uploads the processing-time **`.bin`**, one segment per request via `OmiApiClient.syncSegment`). What each *can* upload differs, so `isAvailableFor` is per-integration: HeyPocket needs the audio to still exist, Omi needs a `.bin` that is only written while Omi sync is enabled — which is why a pre-enable recording is permanently unavailable to Omi and manually uploadable to HeyPocket.
- **`isEnabled` vs `isAvailableFor` is a real distinction, not a synonym.** `isEnabled` gates the *auto*-upload sweep and applies the auto-upload-enabled time cutoff; `isAvailableFor` gates an explicit user tap and deliberately ignores that cutoff, so a user can hand-upload something recorded before they turned auto-upload on. Both fail **closed** on a missing/legacy cutoff timestamp.
- **Lanes are concurrent across integrations, sequential within one** (`_UploadLane`, `IntegrationUploadManager._pumpLane`). Each integration gets its own drain future so a 503ing Omi lane cannot block HeyPocket, but no server ever sees two uploads at once from us. Manual jobs drain ahead of auto-sweep jobs and ignore server backoff. A 503 parks the lane on `busyUntil`; "Upload on Wifi Only" (`uploadOnWifiOnly`) **parks** the lane rather than failing its jobs, and a connectivity change un-parks it. Lane state is in memory only and is rebuilt by the next sweep after an app kill.
- **Cancellation has two scopes and they are not interchangeable**: `cancelRequested` tears down the whole lane (the user disabled the integration or its auto-upload mid-flight), while a single job key bails just that job and keeps draining behind it. In-flight uploads poll `isCancelled` at safe checkpoints — a chunked integration can stop between chunks, a single-shot one only before its request begins — and bail **without delivering and without throwing**.
- **Credentials live in secure storage, never in `SharedPreferences`**: `heypocketApiKey`, `omiIdToken`, `omiRefreshToken` go through `_secureStorage`. Only non-secret state (`heypocketEnabled`, `omiSyncEnabled`, the auto-upload flags, expiry, and the `omiSyncedFiles` / `heypocketUploadedFiles` delivery ledgers) is a plain pref. Keep that split when adding an integration.

**Storage layout** (relative to `getApplicationDocumentsDirectory()`):
- `raw_segments/{timerStart}/{timerStart}_{sessionId}.bin` — one folder per segment, named by UTC epoch-seconds `timerStart`. Pre-time-sync → `raw_segments/session_{sessionId}/`.
- `recordings/{yyyy-mm-dd}/recording_{startMs}.wav` (or `.m4a`) — finalized recording; date is **local** calendar date. `audioSaveFormat` writes only `wav` or `m4a`; OGG was removed and a stored `'ogg'` is coerced to `'wav'`, but the reader still accepts a `.ogg` left on disk by an older build.
- `recordings/{yyyy-mm-dd}/recording_{startMs}_draft.wav` — in-progress flush (always `.wav` — M4A can't be stitched); not surfaced in UI.
- `recordings/{yyyy-mm-dd}/unknown_{startMs}.wav` — recording with derived/uncertain timestamp (time-sync unavailable).
- `recordings/{yyyy-mm-dd}/recording_{startMs}.meta` — binary sidecar: `totalSamples` u32, `durationMs` u32, 200×u16 waveform, `sessionId` u32, `startUptime` u32, upload key, four flag bytes at `flagOffset = 417 + keyLen` (`[0]` passthrough, `[1]` forceSynced, `[2]` capEnded, `[3]` bit0 isSilero / bit1 hardStart / bit2 hardEnd / bit3 modeKnown / bit4 manual / bit5 clockCorrected), JSON relative-bin list. **Never add a fifth flag byte**: the bins-JSON tail is located as `flagOffset + <count>` and the reader infers that count from the meta's *length*, so a new byte shifts the bins section out from under every `.meta` already on disk (empty `relativeBins` ⇒ broken bin pruning and "lists no source segments"). New flags go in byte `[3]`'s free high bits, which every existing reader masks off. The recording **mode** takes two of them — `modeKnown` gating `manual` — because a single bit cannot express "unknown", and every pre-existing `.meta` reads 0; one bit would relabel the whole back catalogue as whichever mode 0 meant. `Conversation.modeLabel` renders `Manual` / `Auto/VAD` / `Auto/AAD`, gated on the `showRecordingMode` display pref (off ⇒ the original bare `VAD`/`AAD`). Legacy metas with `isSilero == true` are promoted to `Auto/VAD` for free — Silero only runs when `vadEnabled` is set and manual mode pins it off, so that bit *proves* not-manual; the converse does not hold (`isSilero == false` is manual, auto-with-Silero-off and auto-with-a-failed-model at once), so those keep the bare `AAD`. `clockCorrected` (0x20) marks a recording the phone re-filed because the Omi's own timestamp was provably wrong; it is the sole gate on the revert arrow, so a genuine device timestamp can never be demoted from the UI. Free bits remaining: 0x40 / 0x80. Every downstream rewrite of byte `[3]` must stay an `|=` — draft promotion and the stitch-append hardEnd carry both preserve the mode bits, and `app/test/unit/recordings_manager_test.dart` pins that.
- `recordings/{yyyy-mm-dd}/marker_{markerMs}.edl` — JSON marker sidecar: `markerTimestampMs`, `segmentFilename`, `markerOffsetMs`, `cropStartMs`, `cropEndMs`, `userSaved`. Orphan markers have empty `segmentFilename`.
- `recordings/{yyyy-mm-dd}/discards.jsonl` — one line per VAD-dropped stretch; surfaced as ghost rows in the UI.

File indices are **cache positions** (0-based sequential) that shift after each deletion — the firmware rebuilds its file-list cache on every CMD_LIST_FILES and after every delete, so after deleting index 0, what was index 1 becomes index 0. Supplying the timestamp in CMD_READ_FILE and CMD_DELETE_FILE lets the firmware re-locate the file by timestamp if the index shifted between LIST and READ/DELETE.

**The app does not read the audio codec, and there is no `BleAudioCodec` type any more.** The firmware still publishes the ID on `0022` (`20` = opus, `21` = opusFS320; current firmware reports `21`, `CODEC_ID` in `lib/core/config.h`) — the characteristic stays, this is only about the phone side.

The whole chain was vestigial, inherited from upstream where a WAL was a chunk of *streamed* BLE audio. Traced end to end before removal: `getAudioCodec()` → `Wal.codec` → serialised to `wals.json` → **read by nothing**; and `Wal.codec.getStorageBytesPerMinute()` → `Wal.estimatedSegments` → serialised → **read by nothing** (the sync UI's "N of M segments" comes from `estimatedTotalSegments`, which counts WAL *entries*). `Wal.seconds` was not even written. Gone with them: the `BleAudioCodec` enum and its frame-size methods, `Wal.mapNameToCodec`, `performGetAudioCodec` and its per-connection cache, and `featuresCodecCharacteristicUuid`. Net effect on the wire is **one fewer GATT read per connection** — the warm-up in `_wakeStorage` was pre-caching the codec for a consumer that no longer exists; the SD-readiness probe there (`performGetStorageFileStats`) is untouched.

**Do not reintroduce a per-frame constant if any of this comes back.** SD-stored frames are **VBR** — measured 61–160 B, mean payload 87.0 B over a 118-bin capture — so a fixed 40/80 B figure (which is what the deleted methods held, modelling MTU-sized stream packets) is wrong about real data. The bin layout is documented under **Audio pipeline** above.

**`wals.json` compatibility.** Removing `codec` / `seconds` / `estimatedSegments` needs no migration going forward: `fromJson` simply stops looking for keys older files still carry. Backwards is bounded rather than clean — an **older** build reading a newer `wals.json` passes `null` into `mapNameToCodec(String)` and throws. That fails safe: the sync path catches it and rebuilds WALs from the device listing (re-downloading any partial transfers from offset 0), and the prune-protection path deliberately propagates so it skips pruning rather than losing bins. No corruption either way — this repo does not otherwise support downgrade.

### Post-DFU bond wipe

**Every successful DFU clears the BLE bond on both sides.** Not a user option, and deliberately not conditional on the firmware version changing.

- **Device**: `ota_mgmt_callback` (`main.c`) watches `MGMT_EVT_OP_IMG_MGMT_DFU_PENDING` — *"the image finished transferring"* — and persists a one-shot `omi/dfu_bond_wipe` flag. `transport_start()` consumes it on the next boot (after bonds load) and calls `bt_unpair`, emitting a forced `DIAG_BOND_STATE` / `DIAG_BOND_CAUSE_POST_DFU` record so an intentional wipe is distinguishable from an unexplained key loss.
- **App**: `releasePairingOnSuccess` calls `unmanageDevice` **then** `removeBond` from the DFU success callbacks (Android only — iOS has no programmatic bond removal).

Invariants worth preserving:

- **`DFU_PENDING`, not `DFU_STARTED`/`STOPPED`.** `STARTED` also fires for an upload that then aborts, and `STOPPED` fires on both completion and abort. Only `PENDING` means "this is really going to be flashed", so only it leaves an aborted transfer's pairing untouched.
- **Never gate the wipe on a version change.** An occupied key slot refuses a fresh Just Works pairing whether the key in it is valid or corrupt (`update_keys_check()` in Zephyr's `smp.c`, with `CONFIG_BT_SMP_ALLOW_UNAUTH_OVERWRITE` unset and `CONFIG_BT_MAX_PAIRED=1`), so a bond a flash corrupts cannot be recovered from the phone. Version-gating skips exactly the same-version recovery reflash a user performs *because* pairing is already broken, and saves nothing — the wipe costs one re-pair the user is already updating through. **A reflash does not necessarily rewrite the app core's slot**: mcumgr skips any image whose hash already matches what the device is running, so a same-version reflash sends *only* the net core (confirmed on-device 2026-08-07 — the app image was skipped, and the DFU progress ring stopped at 41 %, its share of the bundle). The wipe still arms, because `DFU_PENDING` fires for whichever image did land and the net core can never be skipped: the nRF5340 does not report its hash in the pre-upload image list, so mcumgr has nothing to compare and always sends it. Do not restate the rationale as "a flash rewrites the primary slot regardless" — that was the original wording and it is false in precisely the same-version case the rule exists for.
- **The phone must stop reconnecting before it wipes.** The two wipes are seconds apart — the phone's at mcumgr `success`, the device's at the next `transport_start()` — and in between the device still holds the old key while the phone holds none. A connect in that window forces a pairing the firmware *must* refuse (`update_keys_check()`, one occupied slot), so the user gets a system pairing dialog that cannot succeed. Dart's own reconnect paths are gated on `isFirmwareUpdateInProgress`, but reconnection is owned by the native layer and native is gated on nothing: the end-of-flash link drop feeds `handleRetryLogic`, backoff starting at 1.5 s. `unmanageDevice` is the only thing that stops that ladder — release first, wipe second. Reconnection is re-armed by `reconnectWhenDeviceReturns`, which scans until it actually **hears the device advertising again** and only then calls `ensureConnection(force: true, requiresBond: true)`. A sighting is the signal rather than a delay: the swap plus a net-core update takes as long as it takes, and `_clearStaleScanResultsOnSuccess` empties the cache first, so anything seen afterwards is a peripheral heard *after* the flash — i.e. one that has booted, run `transport_start()` and freed its key slot. The pairing dialog still appears on its own; it appears when the device can accept it. A connect that comes back **null** — an explicit failure, most often a pairing request the user has not answered — does not end the loop: it goes back to looking, so the next sighting re-issues the request. If the window expires the screen says so and offers another search, with the manual route in Find Devices behind it. Both halves — the release/wipe order and the sighting-gated reconnect — are held by `app/test/unit/pages/dfuota/firmware_mixin_test.dart`, which drives them against the real `DeviceService` with only the platform channels mocked (peripherals arrive through `BleBridge`, the way native delivers them). They are ordering guarantees, so nothing else catches breaking them: swap the two release calls and the only symptom is an intermittent failure on a real device.
- **The success screen is a waiting room, not a Done button.** Every exit from it goes through `_leaveUpdateScreen` → `postUpdateDestinations`, and while the re-pair has not landed there is deliberately **no primary action at all**: the slot holds a disabled "Waiting for your Omi... / Pairing..." (`_buildPrimaryAction`), because Done being the loudest thing on screen made leaving the default, and leaving disposes the page — which calls `cancelPostFlashReconnect()` and kills the very loop that was about to finish the job. The escape hatch ("Pair manually instead") is present in **every** non-latched state, including a wedged one; that is what makes a disabled primary safe rather than a trap, and it is the only reason no page-side settle timer is needed for a connect that returns but never surfaces as `isConnected`. A back press in that state is redirected to the same destinations rather than popping (`_backLeavesNothingReconnecting`), since a plain pop lands on Device Settings for a device that is not currently paired *and* takes the loop with it; the AppBar button therefore calls `Navigator.maybePop`, not `pop` — only `maybePop` consults the route's pop disposition, so a plain `pop` walks straight past the `PopScope`. An expired window (`PostFlashPhase.timedOut`) offers "Search again" (`retryPostFlashReconnect`, which refuses to clear the one-shot cancel flag while a loop is still running) rather than a dead end. `PostFlashPhase.idle` — iOS, where no loop is armed, and the sliver of a frame before `releasePairingOnSuccess` arms one — keeps the original Done-to-the-scan-list screen, so no platform test appears in the page.
- **Neither screen may outlive the re-pair.** The pairing request comes from the system dialog, so it is accepted with no tap on either app screen — meaning both have to react to `DeviceProvider.isConnected` on their own or they sit there instructing the user to redo what they just did. The success screen watches it through a `Consumer` scoped to that section (`_buildSuccessSection`) and, when connected, swaps the re-pair card for `_buildReconnectedNotice()` and makes Done skip the `FindDevicesPage` push. **What it watches is the transition, not the state** (`_hasRepaired`): a bare `isConnected` read is not a post-repair signal, because the success callback runs `releasePairingOnSuccess` *unawaited* and flips `isInstalled` in the same synchronous block, so the first frame is drawn before the release has closed anything — and native's retry ladder may have re-established the pre-DFU link during the flash, which is the reason the release exists at all. The old link must therefore be seen **down** before a live one counts as the new one. Nothing has to arrive for that in the ordinary case (the device rebooted during the flash, so it is already false on the first frame), and the latch fails in the recoverable direction: a disconnect that never reaches Dart leaves the instructions and the Find Devices fallback up. **And the latch is one-way**: `isConnected` is expected to flap moments after the re-pair, on the commonest path there is — a flash that changes the firmware revision changes the GATT fingerprint, so setup calls `recycleConnection()` to drop Android's stale attribute cache, which is a soft disconnect and a fresh connect. Read live, that walks a user who is now being asked to *wait* for this signal back to "waiting for your Omi". The latch also clears `isFirmwareUpdateInProgress` (which gates background sync and `scanAndConnectToDevice`) the moment it closes, since the user may now sit here for minutes; `_isOnFirmwareUpdatePage` deliberately stays set until dispose, because that is what exempts the link from `_handleDeviceConnected`'s background-drop guard. Getting this wrong is not a cosmetic flicker — leaving also runs the page's `dispose`, which calls `cancelPostFlashReconnect()`, so a user waved through on a stale link is left with nothing at all trying to reconnect. `FindDevicesPage` closes itself on connect (`_onDeviceProviderChanged` → `_closePage`), which is safe because every route into it — the drawer item, the recordings-page bluetooth icon, the Connect Omi button — is gated on being disconnected, so a connected user on that page is on a page they could not have opened. Two things to preserve there: `_closePage` no-ops unless the page's route `isCurrent`, since a tap-initiated connect stacks a loading dialog on top and popping would take that instead — the tap path sets `_closing` and pops both itself; and the post-frame `_onDeviceProviderChanged()` in `didChangeDependencies` covers a page opened onto an already-live link, which the listener alone would leave until some unrelated notification arrived. The per-row pairing mark on that page (green check = connected, grey = bonded) comes from `BleHostApi.getBondedDeviceIds` and **not** from `SharedPreferencesUtil().btDevice`, which still names the device after a DFU wipes the bond and would therefore claim a pairing that no longer exists in exactly the situation the mark exists for. Native enumerates `BluetoothAdapter.bondedDevices` and uppercases — deliberately not a per-address `getRemoteDevice(id).bondState`, which rejects a lowercase MAC outright and assumes a PUBLIC address type this device does not use (see `OmiBleManager.remoteLeDevice`, which reaches for `ADDRESS_TYPE_RANDOM` on API 34+). It is a local read with no radio traffic either way.
- **The device must never infer this from the app.** The retired `0x18` design armed the flag over BLE and gated the phone-side wipe on the write ACK, but the firmware persisted before ACKing, so a lost ACK was indistinguishable from "never armed". The device observing its own DFU removes the inference entirely — do not reintroduce an arm command.
- **Fail toward "device slot free, phone possibly stale."** That direction the user can fix from the phone (Forget Device, `find_devices_page.dart`). The reverse — device bonded, phone wiped — needs the 5-tap-and-hold gesture on the device, because the phone cannot re-pair over a surviving device key.
- **Keep the first-boot migration backstop** (`omi/dfu_wipe_seen`). The flash that installs a given firmware is performed by the *previous* image, so the image introducing any change to this scheme can never have armed its own marker for that flash — while the app clears the phone bond on success regardless. A boot that has never seen the marker therefore wipes once. Removing this would strand every existing device in the unrecoverable direction on exactly one update. The same reasoning applies to any future rework here: the arming half always lags the consuming half by one flash.
- **Not covered**: bond corruption unrelated to a DFU. No `DFU_PENDING` fires, so neither side wipes, and recovery is the 5-tap gesture. Fixing that needs `CONFIG_BT_SMP_ALLOW_UNAUTH_OVERWRITE=y` **plus** `CONFIG_BT_SMP_APP_PAIRING_ACCEPT=y` and a user-presence `pairing_accept` callback — both Kconfigs, see BLE_Research.md §9.

### Timestamp self-correction

**The phone is the Omi's clock of record.** The Omi has no RTC that survives a restart: it learns the time from a connecting phone and forgets it on every boot. Until the next connect it guesses from the IMU's 24-bit, 6.4 ms counter (`lsm6dsl_time_boot_adjust_rtc`) — and that counter wraps every ~29.8 h **in the direction that makes a long gap look short**. An Omi left off for 31 h comes back believing 1.2 h passed and files a day of audio under a confidently wrong date. No bound on the device can catch this, because the wrapped value is entirely plausible.

    correct start = recording startUptime + (phone wall clock − Omi uptime at the same instant)

- **The anchor** (`services/device_clock_anchor.dart`) is one `(sessionId, deviceUptimeMs, wallClockMs)` observation. `DeviceProvider._captureClockAnchor` takes it from a `0x0062` diagnostics read — **all three from the same read**, which is why `device_session_id` was appended to that payload. Pairing an uptime with a session id learned anywhere else reopens the possibility that they describe different boots, and an anchor bound to the wrong boot re-files *correct* recordings to a wrong date.
- **Opportunistic, not "on connect".** `getDropStats()` returns null while a sync holds the storage mutex, so an anchor is taken whenever a diagnostics read gets through. That is enough — an anchor describes a boot, and the boot does not change. Never force the read past the mutex to guarantee one: a GATT read racing the storage stream throws Error 133 on Android and costs the sync.
- **Valid for exactly one hardware session.** Each boot takes a fresh random `device_session_id` and restarts uptime at zero, and the gap between two sessions is unmeasurable — both counters reset when the Omi dies. A session the phone never saw running therefore keeps whatever the Omi assigned and stays Unorganized. That is the honest answer, not a limitation.
- **Anchors are kept per session, several at a time** (`DeviceClockAnchorSet`, bounded at 8, oldest evicted). An anchor outlives its session: recordings can still be unsynced on the SD card when the Omi reboots, and they arrive placeable only if their session's anchor survived the reboot. One slot would discard the answer at exactly the moment the device's own clock became least trustworthy.
- **Three rules, and no tuned threshold** (`clockVerdict`): a recording that already agrees is never touched; one with no timestamp is given one; one the anchor can *prove* wrong is overwritten. Ordinary drift (seconds) and a wrapped guess (~29.8 h) are four orders of magnitude apart, so `plausibleDriftMs` only has to land somewhere in between — it is a deliberate 1000 ppm over-estimate with a 60 s floor, not a tuning knob.
- **Whole sessions move together**, because a session has exactly one offset. `RecordingsManager.applyClockAnchors()` runs from `_finishPipelineRun()` and delegates every rename to the existing `promoteSessionToDate()` — audio, `.meta`, `.bin` and `.edl` markers all move there, and no second file-moving path should ever be written.
- **Idempotent by construction.** After a move the session agrees with its anchor, so the next pass reads `alreadyCorrect`.
- **A revert needs the ledger, not just the anchor** (`ClockCorrectionLedger`, pref `clockCorrectionLedger`). Discarding the session's anchor is necessary and *not sufficient*: the anchor is re-captured from any later diagnostics read, which is every reconnect while the Omi stays on the same boot, so the next pass would find the session disagreeing with a fresh anchor and re-file it — silently reversing the user. `applyClockAnchors` therefore skips any session the ledger marks reverted, permanently. The ledger also stores the offset the session's recordings carried **before** the first correction, captured before the move because the move is what destroys it — the offset lives only in the filenames `promoteSessionToDate` rewrites. Without it an undo has nothing to restore; reading the uptime as an epoch instead (an earlier version of this) lands the session in 1970 rather than on the date the Omi had filed. A second correction must **not** overwrite that stored offset — the first is the one that moved the recordings off the device's own timestamps.
- The revert arrow is gated **only** on `.meta` flag `0x20`, so the affordance can only ever undo the app's own work, never a timestamp the Omi assigned and the phone agreed with.

## Verify every change adversarially, end to end

**Do this for every change, without being asked, before reporting it done.** Not a re-narration of
what you wrote — an attempt to break it. Each rule below is here because skipping it cost a round.

1. **Trace the whole path, not the diff.** Follow the change from its trigger to its effect through
   the real call sites. Two bugs in one session were found this way and by nothing else: a
   `_failSyncCycleToIdle` that moved the alarm but not the Dart timer, and a battery line fixed in
   Dart while the Kotlin renderer — the one that runs when Dart is frozen, i.e. the actual failure
   case — kept the old text. `grep` for the string you changed; assume there is a second copy.

2. **A claim in a comment or commit message is a claim.** Verify it or don't write it. "This can't
   be reached", "that path already handles it", "the compiler enforces this" — check. The
   `return_without_value` guarantee in `_doBackgroundSync` was verified by mutating the source and
   running the analyzer, which took a minute; asserting it would have been a coin flip.

3. **Ask what the fix now makes reachable.** A fix that stops suppressing something means that
   something now happens. Clearing `lastSyncSkipped` correctly turned an adoption path back on that
   had been dead — which then exposed a re-entrancy guard swallowing it. The second bug only
   existed once the first was fixed.

4. **Find the docs and comments the fix just falsified.** Code and prose drift silently. Fixing the
   native log writer invalidated a "THREE WRITERS SHARE THIS FILE" comment, a `WedgeDiagnostics`
   rationale, and a NOTES section that *blessed the bug as intentional*. A stale invariant is worse
   than none: the next reader restores the bug on purpose.

5. **A test that cannot fail is not a test.** Mutate the source so the test should fail, run it,
   confirm it does, revert. Especially when a metric already declared the area fixed — the 0.34.9
   log-loss fix was validated by counting unparseable lines, which structurally cannot see a record
   overwritten whole, so a real fault read as clean for a year. **Ask what failure your check cannot
   express.**

6. **State residuals; don't quietly leave or silently "improve" them.** If something is bounded but
   not airtight, say so, in the report and in NOTES, with the shape a real fix would take and the
   tempting wrong one spelled out. If a fix needs scope you weren't given, say that instead of
   half-doing it.

7. **Report what you verified, what you cleared, and what you couldn't test.** "Checked and cleared"
   is useful to the reader — it says the obvious objection was considered. "Not unit-tested because
   no test here constructs a real `DeviceProvider`" is an honest and actionable statement; silence
   implies coverage that does not exist.

## Dead code

Three rules, because "this looks unused" cost a review round once and will again.

1. **"Dead" is a claim, not an impression.** It gets the same verification as a bug claim — trace the callers before saying it out loud. `SDCardWalSyncImpl.start()` was called "dead", twice, before anyone checked. It was *reached* every launch and simply could not do its job there — `getMissingWals()` returns at its `_device == null` guard, because `ServiceManager.start()` runs before any device is registered. Reached-but-inert and unreachable are different findings with different fixes, and the difference paid: tracing it turned up a second thing nobody had claimed, which is that it could overwrite `_wals` from a `.then()` racing a running `syncAll()`. So it was **deleted rather than guarded** (rule 2), and `IWalSync` now carries a "No `start()`" note saying why — the method no longer exists, and `WalService.start()` is a different thing. Treat the removal, not the method, as the example.

2. **Once verified: delete it, or give it a stated reason to exist.** Never a third state of "mentioned in a review comment" — that is how a codebase fills up with notes about things nobody will ever action. Two reasons are already precedented here and both are good: it is a **wire/ABI compatibility artifact** (the retired `0x18` opcode that older app builds still emit; `register_button_service()`, whose removal would shift every later handle and cost a re-pair), or it is a **backstop for a state you cannot currently produce but a future flash/version can** (`omi/dfu_wipe_seen`, where the arming half always lags the consuming half by one flash). If neither applies, it goes.

3. **An unreachable inconsistency is not a review finding.** Either it is reachable — then it is a real finding with a real failure mode — or it is not, and the only honest output is "delete this", filed on its own rather than folded into a review of behaviour. A reviewer who reports "these two paths disagree, but one is unreachable" has spent the reader's attention making them re-derive the reachability just to dismiss it.

## Git

- Always commit to the current branch — never switch branches.
- Never squash merge PRs — use regular merge.
- Make individual commits per file, not bulk commits.
- If push fails because the remote is ahead: `git pull --rebase && git push`.
- Never push or create PRs unless explicitly asked — commit locally by default.

### RELEASE / release command
When the user says "release" or "RELEASE", increment the patch digit in `app/pubspec.yaml` by 1, commit, and push. The patch digit serves as the build number — there is no separate `+N` suffix. Example: `0.3.18` → `0.3.19`. After the bump, `app/build.sh` can produce the matching `oo<digits>.apk` at repo root (deterministic, no extra git ops).

Document user-visible behavioural changes in `CHANGELOG.md`, which has two top-level sections — `## App` and `## Firmware` — each with newest on top. Entries are keyed by **minor** version (`### 0.36`), not by patch: a patch bump folds into the existing minor section rather than opening a new one, and each section states the **net** behaviour at the end of that series, so superseded or reverted intermediate steps are edited out rather than appended to. `README.md` only links to it.
