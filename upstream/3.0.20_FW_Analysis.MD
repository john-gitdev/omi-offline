## Key architectural context (why some items don't port)

- **AAD history:** hardware AAD did NOT exist at 3.0.19. Both upstream 3.0.19 and omi-offline run **software VAD** (`aad.c`, from upstream `f8e3357766` "handle AAD by software"). Our `aad.c` is upstream's 3.0.19 `aad.c` (350 lines) extended to 546 (markers, pre-roll, force-wake, priority). The WAKE-pin ISR + `pdm_en_pin`/`pdm_thsel_pin` DTS nodes are inherited scaffolding — wired but never engaged (the T5838 is never put in AAD mode). **3.0.20's `t5838_aad.c` (`27f41e8aab`) is the first real hardware-sleep implementation in this lineage** — the missing piece our scaffolding was built toward.
- **Storage:** ours = LittleFS over disk_access (SD-SPI stack) with a file-index LIST/READ/DELETE + WAL protocol the app depends on. Upstream 3.0.20 = raw NAND ring buffer. Different wire format.
- **Storage part (datasheet, 2026-07-17):** `CSNP4GCR01-DPW` (CS Semiconductor / Creat Storage World) — a **4 Gb (512 MB) SD-NAND**: a NAND die + SD controller in one LGA-8 package, presented over SD-SPI (`sdhc0: zephyr,sdhc-spi-slot` + `mmc: zephyr,sdmmc-disk`, `omi_nrf5340_cpuapp.dts:209`). VCC **2.7-3.6 V**; **operation current 15-25 mA** (read/write bursts), **standby < 200 µA** (CS high, unclocked); **no command-reachable deep sleep** — it is *not* a raw SPI NAND, so there is no `0xB9`/`0xAB` deep-power-down or CMD5 sleep. Consequence: NAND power-gating means cutting **VCC** (via `sd_en`), which loses the SD session → full re-init + LittleFS remount/scan (the hazard in items 1/13). Standby is the only mount-preserving low-power state, and we already reach it in silence via `sd_set_io_low_power` (suspends `sd_dev` + `spi3`). Datasheet: LCSC `C2691595`.
- Our software-VAD model writes `0xFFFFFFFD` VAD-resume markers + pre-roll into the bin stream; the app pipeline depends on a continuous stream. A truly-sleeping mic changes when/how those emit (see items 1, 13).

## Findings (2026-07-17): runtime battery is a RAM-budget problem, and full NAND-off is off the table

Primary goal is **reliability + audio capture**. That reorders everything below.

### Full NAND power-off during silence (the item 1/13 "runtime battery" prize) is NOT feasible for a capture-first device

Two failure modes, both attacking capture directly:
1. **Full-FS remount = 10-50 s deaf window.** The LittleFS allocator pre-warm scan reads every block in every file — "10-50+ seconds per scan over SPI" at 200 MB (`sd_card.c:117-118`). The FS is full exactly when the user hasn't synced for a long time — the same condition where battery savings matter most. So the mechanism fails hardest in its own best case: power off to save battery → miss the first 10-50 s of the conversation that wakes it. No pre-roll buffer can cover that.
2. **Wake-remount can wedge until reboot.** Already documented as the reason the current design rejected this: "a full power-off + remount-on-wake could persistently fail (driver wedge) and latch `sd_write_blocked`, silently killing recording until a reboot" (`sd_card.c:346-351`).
   (Plus best-case onset clipping from wake latency + lost pre-roll.)

**⟹ Keep the NAND mounted + powered whenever the device is running. This is a correct reliability call, not a missed optimization.**

### The only viable runtime-battery path: reduce draw while staying mounted (never power-off + remount)
- **Deeper SPI-bus suspend in silence** — already done (`sd_set_io_low_power`); mount stays live, no scan, no wedge. Measure how much more it can give.
- **Mount-preserving NAND standby** — ✅ RESOLVED (2026-07-17, datasheet-checked): the CSNP4GCR01 is an **SD-NAND** (SD-over-SPI, `zephyr,sdhc-spi-slot`), VCC 2.7-3.6 V, **operation 15-25 mA / standby < 200 µA**, and has **no deeper command-reachable sleep** (no DPD/CMD5 — that's raw SPI NAND, which this is not). Standby (CS high, unclocked) is the only mount-preserving low-power state — and **we already reach it during silence** via `sd_set_io_low_power` (suspends `sd_dev` + `spi3`). So there is **no untapped NAND-side runtime lever**; going below ~200 µA needs VCC-off = the non-viable remount/scan path.
- **Ship-mode pin parking (items 10-12)** — zero capture risk (device already off).
- Mic + nRF idle draw = hardware-AAD territory (item 1), but that carries its own onset-clipping capture cost.

### Ring buffer (item 2) is the WEAKER RAM lever — not needed, doesn't help
Our storage RAM: `sd_msgq` ~45.6 KB (100 × `sd_req_t` embedding `buf[440]`) + `write_batch_buffer` 44 KB + LFS caches ~22.5 KB + worker stack 16 KB. The two big consumers (~90 KB) are **backend-agnostic write buffering** — upstream's ring-buffer firmware *still* has `sd_msgq`. The ring buffer only reclaims the ~22.5 KB of LFS caches. The pattern worth stealing is upstream's `K_MEM_SLAB` block staging (`mic.c:48`), **not** the ring buffer.

### RAM is a seesaw; runtime battery is really a RAM-budget problem
History: mem_slab (`081bf6eff`, ~68 KB freed) reverted the **same day** (`8185fe644`) because "nothing needed the RAM." `write_batch_buffer` removed (`a9588ccb8`) then re-added. `AUDIO_BUFFER_SAMPLES` shrunk then regrown to 32 KB. Then the AAD/VAD pre-roll rings landed (`aad.c`: `vad_preroll_buf` + `vad_live_backlog_buf` ≈ 51 KB, oo-1.4.0 `252d3b0f1`) and ate the entire ~37 KB reclaim → **net RAM ≈ 0**. Image is ~91 % full.

The chain: runtime-battery power-off is gated on remount latency → covered by pre-roll depth → gated on RAM → gated on redoing the slab reclaim. The slab revert's premise ("nothing needs the RAM") is now **false** — pre-roll growth is the consumer. But every reclaim so far got eaten within days, so the rule is **reclaim AND spend in the same change, with drop-testing** (`sd_msgq_peak_depth` / `stat_dropped_frames`), never "free RAM and hope."

## Battery conclusion (2026-07-17)

For a capture-first device, **item 10 (the ship-mode PDM_EN leak) is the end of the road for capture-safe battery wins.** The reasoning is now fully closed:
- **NAND side — no lever.** Datasheet-confirmed: SD-NAND standby is < 200 µA, already reached in silence via SPI suspend; there is no deeper command-reachable sleep, and going lower (VCC-off) triggers the remount/allocator-scan/wedge hazard that is non-viable for capture (items 1/13, `sd_card.c:117-118`, `:346-351`).
- **The runtime draw that remains** during a silent-but-on period is the **nRF (CPU/BLE/PDM) + the T5838 mic streaming continuously for software VAD** — i.e. **hardware AAD (item 1)**. Cutting it clips word-onsets (lost pre-roll + wake latency) and forces a marker-pipeline rework.
- **So further runtime battery is a product tradeoff, not a free win:** it means accepting some auto-mode onset clipping in exchange for mic/nRF sleep. Off the table under the current reliability-first priority; only revisit if that tradeoff becomes acceptable in auto mode specifically.

## D. Power / current reduction (net after reverts)

### 10. Cut PDM_EN in `mic_off` `[power]` — ✅ DONE  **KEPT upstream**

Committed to `main`; **build + on-device current-meter verification still pending** (no local nRF toolchain — the ~1 mA saving is unmeasured).

### 11. Park CLK/THSEL high during AAD sleep `[power]` — ❌  **KEPT upstream**
Kills TXS0104 shifter leak (~1 mA) — held low they fight the shifter's 10k pull-ups. Commit: `6252383b54`.
Notes: only meaningful once we actually enter a sleep state (couples to item 1).
**Decision:** ❌ skip — AAD-sleep-coupled. Upstream parks CLK/THSEL HIGH *during AAD sleep with the shifter still powered*; we have no such state (not on hardware AAD), and at ship-mode item 10 unpowers the shifter, so HIGH would forward-bias it (regress). Correct polarity here is low/high-Z; ~0.5 mA/rail, high uncertainty — not worth it vs item 10. Revisit only with a current meter.

### 12. Park SD chip-select low during sleep `[power]` — ❌  **KEPT upstream**
Stops pin leak into unpowered card; `gpio_pin_set_raw`. Commit: `b5c2722710`. Couples to item 13.
**Decision:** ❌ skip (for now) — we already set CS (`gpio1/11`) to `GPIO_DISCONNECTED` at power-off (`sd_card.c:825`); upstream's fix targets the SPI driver *idling CS high*, which we don't do. Flipping disconnect→driven-low needs confirming the existing "MOSI hold / back-feed" disconnect isn't load-bearing. Marginal; revisit with a meter.

### 13. Power off SD NAND during AAD sleep, remount on wake `[power]` — ❌  **KEPT upstream**
