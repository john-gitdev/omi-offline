# 3.0.20 port tracker — re-evaluation for the ring era

Companion to [`3.0.20_FW_Analysis.MD`](3.0.20_FW_Analysis.MD). That document reached its
verdicts on **2026-07-17**, against a fork that ran **LittleFS over disk_access** and drove
**PDM_EN** at ship-mode. Both of those are gone. This doc re-runs only the items whose
*premises* changed, and answers one question:

> **Given we're on the ring now, is anything from upstream 3.0.20 portable?**

**Short answer: three things, in this order — pin parking (free, do it), SD power-off in
silence (newly feasible, ≤200 µA), hardware AAD (the only large auto-mode lever, and a
capture tradeoff).** Nothing about the ring rewrite itself is portable; our ring is an
independent implementation with a different wire protocol.

_Verified 2026-08-08 against this tree at `oo-2.9.2` and against the upstream repo on disk at
`../omi` (firmware nested at `omi/firmware/omi`). All code claims below are current-tree
reads, not carried forward from the older doc._

---

## What changed since 2026-07-17

Five facts, and each one invalidates at least one verdict in the old doc.

| Change | Where | Consequence for the old verdicts |
|---|---|---|
| **LittleFS removed**, replaced by our own raw append-only log | `oo-2.9.0`, `sd_ring.c` | Kills the primary objection to items **1** and **13** — the 10–50 s allocator-scan remount. Mount is now `CTRL_INIT` + one header sector + segment table. |
| **40 KB ring stage** buffers ~8 s of audio before touching NAND | `sd_ring.h:111`, `sd_card.c:120` | An SD power-cycle (~100–300 ms) is now absorbed in RAM with ~25× margin. Item 13's "deaf window" is no longer a capture risk, only a durability one. |
| **Item 10 was reverted** — nothing drives PDM_EN any more | `oo-2.8.5`, `7499dfdd`, IDEAS.md #5 | The old doc's closing line ("item 10 was the only actionable win") now nets to **zero** upstream power items live in this tree. |
| **~48 KB of RAM free**, and no LFS caches | build-verified 2026-08-08: bss 401,486 / 450,560 | The old doc's blocking chain ("power-off gated on remount latency → covered by pre-roll depth → gated on RAM") has its RAM gate open. See the pre-roll correction below. |
| **The device is run in AUTO mode**, not the default manual | owner, 2026-08-08 | Any lever that only pays in manual standby is near-worthless here. Auto mode needs acoustic sensitivity at all times, so mic-down states require hardware AAD — item 1 — not a simple `mic_pause()`. |

### One correction to the old doc's reasoning

It states the power-off path is "gated on remount latency → covered by pre-roll depth."
**Pre-roll cannot cover mic deafness** — it is filled *by* the running mic, so a sleeping mic
produces no pre-roll to spend. Pre-roll (and more usefully, the ring stage) covers an **SD**
outage, where audio keeps flowing into RAM while the card comes back. That distinction splits
the two items cleanly:

- **Item 13 (SD off)** — buffering solves it. We already have 8 s of it.
- **Item 1 (mic off)** — no amount of RAM solves it. The audio does not exist.

## Portable now, in priority order

### P1. Pin parking + explicit PDM disable — free, no AAD required, do it first

**Upstream items 11 and part of 1.** Source: `../omi/.../src/t5838_aad.c:152-158,178-184` and
`../omi/.../src/mic.c:324-333`.

The finding that makes this urgent rather than academic:

- `nrfx_pdm_stop()` **never disables the PDM peripheral** — verified, `nrf_pdm_disable` appears
  nowhere in `nrfx_pdm.c` (NCS v2.9.0). Upstream hit this and wrote `pdm_hw_disable()` with the
  comment *"dmic STOP alone does not reliably release the CLK pin."*
- So after any `dmic_trigger(DMIC_TRIGGER_STOP)`, PDM0 still owns the CLK/DIN PSELs and holds
  **PDM_CLK driven low**.
- Upstream: held low, CLK and THSEL *"fight the TXS0104's internal 10k pull-ups on both rails
  (~0.5 mA each). High matches the pull-ups → no shifter leak."*

**We already have a mic-down state in production: mute.** `mute_apply()` → `mic_pause()`
(`button.c:129`, `mic.c:241-255`) stops the dmic and nothing parks the lines. So every muted
stretch plausibly costs ~0.5–1 mA for nothing — on a 150 mAh cell, in a state a user can sit
in for hours. Same applies to the boot window before `mic_start()`.

What to lift, verbatim in behaviour:

```c
/* on entering any mic-down state */
mic_pause();                 /* existing */
nrf_pdm_disable(NRF_PDM0_S); /* release the CLK pin - nrfx_pdm_stop() does not */
clk_set(1);                  /* park PDM_CLK high: matches the shifter pull-ups */
gpio_pin_set_dt(&thsel, 1);  /* park THSEL high */

/* on leaving it */
gpio_pin_set_dt(&thsel, 0);
gpio_pin_configure(clk_port, PDMCLK_PIN, GPIO_INPUT); /* pinctrl reclaims on next START */
mic_resume();
```

Pin map is identical to ours — PDMCLK P1.1 (`omi-pinctrl.dtsi:39`), `pdm_thsel_pin` P1.5,
`pdm_en_pin` P1.4, `pdm_wake_pin` P1.2, all already in `omi_nrf5340_cpuapp.dts:57-71`.

**Polarity warning, carried from the old doc's item 11 and still valid:** park HIGH only while
the shifter is *powered*. Since `oo-2.8.5` nothing drives PDM_EN and a board pull-up holds the
rail up permanently, so powered is always the case here — but if PDM_EN driving ever returns
(IDEAS.md #5 step 3), a HIGH park into an unpowered shifter forward-biases it. Tie the park
polarity to rail state if that day comes.

**Capture cost: none.** This changes no state the audio path can observe.
**Risk:** touching the mic subsystem at all, during an open wedge investigation. Mitigated by
scope — it only runs in states where capture is already stopped.
**Prize:** ~0.5–1 mA × time-spent-muted. Unmeasured; a meter settles it in minutes.

### P2. Item 13 — power the SD NAND off during silence: premise dead, now feasible

Upstream: `1821c04a6a`, wired into `enter_hw_aad`/`exit_hw_aad`
(`../omi/.../src/mic.c:377-379,402`) as `sd_request_power(false/true)`.

Old verdict: **❌ NOT FEASIBLE.** Two objections. Re-checking both against the ring:

| Old objection | Status today |
|---|---|
| "Full-FS remount = 10–50 s deaf window" — the LittleFS allocator pre-warm reads every block of every file | **Dead.** There is no allocator and no free-map. `sd_mount()` (`sd_card.c:626-699`) is: `sd_enable_power(true)` → 50 ms settle → `DISK_IOCTL_CTRL_INIT` (retry ladder 50/100/150/200/250 ms) → `sd_ring_mount()` = header sector + CRC32 + segment table. Order **100–300 ms**, and flat in card fullness — the property that made the old objection fatal (worst at exactly the moment savings matter most) is gone. |
| "Wake-remount can wedge until reboot and latch `sd_write_blocked`" (`sd_card.c:227-232`) | **Survives — but weaker.** We now power-cycle + remount **in production** as the recovery escalation (`SD_RECOVERY_REMOUNT_THRESHOLD`, 3 failed soft recoveries), so the path is exercised rather than theoretical. Field evidence for how often it fails is what's missing. |

And the ring adds a third property the old doc couldn't have credited: the **40 KB stage is an
8-second shock absorber**. Writes land in RAM and only reach NAND on flush, so a 100–300 ms
re-init is invisible to capture — no lost audio, only deferred durability. Loss on an unclean
cut is unchanged (bounded by `RING_SYNC_BYTES` 256 KB / the 60 s fsync), because the ring is
append-only and bytes past the last cursor were never claimed.

**But size the prize before building it.** The old doc's datasheet work is still the binding
constraint and does not change with the filesystem: CSNP4GCR01-DPW standby is **< 200 µA**,
there is **no command-reachable deep sleep** (not a raw SPI NAND — no 0xB9/CMD5), and
`sd_set_io_low_power()` already reaches standby during silence. So the entire remaining prize
is **≤200 µA**, bought with a VCC cut and a re-init on every wake.

**Verdict: reclassify ❌ NOT FEASIBLE → 🟡 feasible, low prize, do after P1 and only with a
meter.** If measurement shows the card idling near 200 µA it's ~5–8 % of a plausible idle
budget and worth the wedge risk only with the recovery path hardened. If it idles under
~100 µA, drop it permanently and record the number so this doesn't get re-litigated a third
time.

Instrumentation already exists for the risk: `ring_max_io_ms` (`0x0062` offset 76) and
`ring_io_errors` (offset 80) will show remount stalls and I/O faults directly, and
`sd_msgq_peak_depth` shows whether the stage absorbed the outage.

Pair with **item 12** (park SD CS low during sleep, `b5c2722710`) if adopted — though note we
already set CS to `GPIO_DISCONNECTED` at power-off, and the old doc's caution stands: flipping
disconnect→driven-low needs confirming the MOSI back-feed hold isn't load-bearing.

### P3. Item 1 — hardware AAD: the only large auto-mode lever, and the one real tradeoff

Old verdict: **❌ skip** — conflicts with software VAD, clips word onsets. That verdict was
reached for a *manual-default* device. **The owner runs auto mode**, which inverts the
importance: in auto mode the mic path is the dominant continuous draw and there is no cheaper
way to touch it.

The ring changes nothing here — this was never a storage question. What *has* changed is that
the port is smaller than the old doc implies, and the driver is on disk:

- **`../omi/.../src/t5838_aad.c` — 190 lines, raw GPIO, no Zephyr driver model, no DTS binding
  needed.** FAKE2C bit-bang (unlock sequence + Mode A), `t5838_aad_enter()` /
  `t5838_aad_release_clk()` / `t5838_aad_power()`. Our pin map matches exactly.
- Nothing equivalent exists in NCS v2.9.0 (`zephyr/drivers/audio/` has no t5838), and our
  `pdm_wake_pin` ISR in `aad.c:252-260` is scaffolding that **cannot fire today**: nothing ever
  puts the mic into AAD mode, and AAD only operates with the PDM clock stopped.
- Upstream's numbers: mic in AAD sleep **~20 µA**; `AAD_PDM_SETTLE_MS` 20 ms on the wake path;
  `CONFIG_OMI_AAD_SETTLE_MS=800` on the entry path to swallow the transient.
- Their state machine is 4 atomics + a semaphore-blocked thread with no periodic poll
  (`../omi/.../src/mic.c:363-451`) — close in shape to our existing `aad_thread_fn`, which
  already handles the SD pause/resume and advertising requests the same way.

**What it actually costs us, itemised — this is the decision, not the code:**

1. **Sensitivity drops, and not by a little.** Mode A at 75 dB wakes on *nearby speech* by
   upstream's own comment; 60 dB "triggers on ambient noise". Our software gate is
   `CONFIG_OMI_VAD_ABS_THRESHOLD=250` on `avg|PCM|` — far more sensitive. Quiet or across-the-
   room speech that we capture today would simply never wake the mic. For a device whose value
   is *not missing conversations*, this is the real cost, and it is not recoverable by tuning
   the host side.
2. **The 0.8 s pre-roll is gone** (`VAD_PREROLL_FRAMES` 8 × 100 ms, `aad.c:103-107`). Today we
   record *backwards* from the trigger, so a conversation starts with its first word intact.
   With AAD the mic is deaf until the acoustic event, then needs ~20 ms of PDM settle: the
   first syllable is clipped. Combined with (1), the honest framing is **~0.85 s of context
   lost per wake, plus every conversation that never gets loud enough to wake it.**
3. **RAM would come back, not get spent.** Killing pre-roll + live-backlog frees ~51 KB
   (`vad_preroll_buf` + `vad_live_backlog_buf`, 8 × 3200 B each). On top of today's 48 KB free
   that is a lot of headroom — and per the old doc's own lesson ("reclaim AND spend in the same
   change"), decide what it funds before removing it.
4. **App-side impact is smaller than the old doc feared.** The pipeline already tolerates
   discontinuity: the firmware emits `0xFFFFFFFD` VAD-resume markers on every wake, and the app
   stitches file gaps up to `vadSplitSeconds - _firmwareVadHoldMs`. A sleeping mic produces the
   same marker at the same point in the stream. What changes is *frequency* of wakes and the
   loss of pre-roll audio ahead of each one — a quality change, not a protocol change.

**Verdict: keep ❌ for auto-mode default, but reclassify the reason.** It is not an
architecture conflict and not a big port — it is a deliberate exchange of capture sensitivity
for battery. The only configuration where it is clearly correct is one where the user has
*said* they'd rather miss quiet speech than charge daily. If it is ever attempted, gate it
behind a runtime setting (a new characteristic on a last-registered service, per CLAUDE.md's
handle-shifting rule) and keep software VAD as the default path, so the comparison can be made
on-device instead of in a doc.

## Not portable: the ring rewrite and everything hanging off it

**Items 2, 3, 9.** We already have a ring — ours (`sd_ring.c`), an independent implementation.
Upstream's is a different on-card layout and a different wire protocol (they rewrote the sync
methods and added `RING_INFO`/`sd_ring_info_t`/`read_seq`; we kept the file-index
LIST/READ/DELETE + WAL protocol the app depends on). Nothing here is cherry-pickable, and
item 2 is now moot rather than rejected.

**But their bug list is a free test checklist for ours** — same data structure, same hazards,
already debugged on real devices. Worth reading these diffs against `sd_ring.c` specifically:

| Upstream commit | What it fixed | Check in ours |
|---|---|---|
| `b49faed668` | drain-on-idle-power-off | Do we drain the stage before `sd_enable_power(false)`? (`sd_unmount()` syncs — confirm the msgq is drained too, and that P2 above doesn't open a hole here.) |
| `54c0e71478`, `fa8b62f016`, `f1bb20c7d1` | `read_seq` race + file-list hardening | Our equivalent is the segment table + `RING_SEG_FLAG_OPEN` exclusion. Race audit against a concurrent rotate. |
| `56e0d3b220` | `STORAGE_NOT_READY` status | We have `sd_boot_ready` + the read-control status byte. Cross-check the not-ready path returns something the app handles. |
| `cf6e03974b`, `1cdad8d341`, `f35558fe4d` | hold sync response until mounted; wait ≤5 s for SD ready | Ours waits for SD-ready; confirm the ring's mount-in-progress window is covered too. |

**Item 3 (~100 KBps sync)** was rejected as ring-entangled. Now that we're on a ring it's worth
one look — but the structural source of their win is sequential reads without FS overhead, and
`sd_card.c:287-289` says we already have exactly that ("a segment read resolves to a byte range
in the log and goes straight to disk_access, with none of the open / seek / close cost a
filesystem charged per read"). Measure our current throughput before assuming there's a gap.

## Verdicts that do NOT change

Recorded so they stay settled.

- **Item 17 (BLE low-power conn params during sleep) — ❌.** Upstream tried aggressive slow
  interval + slave latency and **reverted it**; the scar is still in their code:
  *"forcing slow interval + slave latency here was causing dropped BLE connections"*
  (`../omi/.../src/mic.c:373-374`). Independent of storage. Do not retry on a link we've spent
  months stabilising.
- **Item 16 (LED off during sleep) — ❌.** Upstream reverted it themselves. Separately verified
  local: `pwm_nrfx` stops the peripheral at 0 %/100 % duty, so our idle LED costs nothing.
- **Item 15 (IMU power-off during run) — ❌.** Breaks `lsm6dsl_time_prepare_for_system_off` →
  `lsm6dsl_time_boot_adjust_rtc`. Also pointless: verified in the NCS driver that both ODRs
  default to power-down, `XL_HM_MODE`/`G_HM_MODE` are set to low-power, our 0 Hz gyro request
  *is* accepted (`lsm6dsl_odr_map[0] == 0`), so the IMU already runs at tens of µA.
- **Item 10 (PDM_EN cut at ship-mode) — deliberately given back.** Reverted in `oo-2.8.5` to
  isolate the mic-wedge variable; ~1 mA ship-mode leak is the accepted price. Restore order and
  conditions are in IDEAS.md #5 — the rail cut is step 3, last, and only with the `turnoff_all()`
  bail paths still rebooting.
- **Items 7, 8 — 🟡/✔️ unchanged.** TX-buffer reservation is still the only way to drop the
  sync-time battery-detail suppression (`transport.c`). Storage-independent; low priority.
- **Items 5, 14, 18, 19, 20 — unchanged** (already have / housekeeping / own bonding design).

## Adjacent local findings (not upstream, but they interact)

Found 2026-08-08 while auditing this; recorded here because they change the arithmetic above.

1. **`CONFIG_SERIAL=y` with no consumer.** Zephyr's UARTE driver is built and, at init, enables
   UARTE0 and leaves **STARTRX armed forever** (`uart_nrfx_uarte.c:614-617`) — while
   `CONSOLE`/`PRINTK`/`UART_CONSOLE`/`SHELL` are all off, `CONFIG_LOG` is absent, and RTT isn't
   enabled. It is a fork artifact: upstream still runs a real console (`CONFIG_CONSOLE=y`,
   `PRINTK=y`, `UART_CONSOLE=y`), so `SERIAL=y` is correct *there*. `CONFIG_SERIAL=n` builds
   clean here (full sysbuild, exit 0, DFU zip produced; text −984 B).
   **This is a prerequisite for P3 to pay off** — an RX-armed UARTE holds the same 16 MHz clock
   domain the PDM does, so putting the mic to sleep with the UARTE up leaves the domain awake.
2. **The mic path holds HFXO explicitly.** Our `&pdm0` node sets
   `clock-source = "PCLK32M_HFXO"` (`omi_nrf5340_cpuapp.dts:173`), which makes the dmic driver's
   `request_clock` true, so it takes an onoff request on HFXO for as long as the stream runs
   (`dmic_nrfx_pdm.c:426-431`). Quantifies why the mic path is the dominant idle term, and why
   P3 is the only lever that reaches it.
3. **Manual standby could stop the mic outright, no AAD needed** — in manual standby
   (`vad_threshold == 32769`) no sound can start a recording, since `avg|int16|` cannot reach
   32769 (`aad.c:343`). Worth noting for completeness and for other users, but **near-worthless
   for this device**, which runs auto mode.
4. ~~**Ring stage 40 → 80 KB** spends spare RAM to halve the NAND flush rate while recording
   (tens of µA).~~ **Withdrawn 2026-08-08 on device data — do not do this.** A 22 h snapshot
   (`oo-2.9.1`, auto mode) read `queue: peak=60/120`, `ring: maxIo=553ms(write) ioErrors=0`,
   and **zero drops**. `note_io()` wraps a single `disk_access_write`, and
   `flush_full_sectors_ex()` issues the stage as `RING_FLUSH_CHUNK_SECTORS`-sized ops, so a
   full 40 KB stage is **10 chunks**: a flush in which the FTL is slow on each of them holds
   the worker ~5.5 s, which at the measured ~11.6 blocks/s queues ~64 blocks. Observed peak 60.
   The queue is therefore already sized around one worst-case full-stage flush, with 50 %
   headroom and nothing lost. Doubling the stage doubles the chunks per flush (20), so the
   worst case becomes ~11 s ≈ 128 blocks — **past the 120-slot queue, i.e. dropped audio** —
   to save tens of µA. `allow_yield` does not help: it breaks the flush for a waiting BLE
   *read* (`io_busy()` = prio msgq only), never for pending audio writes.

## Sequencing

1. **Measure first.** PPK2, four states × 5 min: auto-silent disconnected / muted / recording /
   syncing. Every number in this doc that matters is unmeasured, and the candidates differ by
   10×. The muted state is the cheapest possible test of P1's premise.
2. `CONFIG_SERIAL=n` (local finding 1) — free, and it unblocks the P3 measurement.
3. **P1 pin parking** — apply to mute + boot. Re-measure the muted state; the delta *is* the
   shifter leak.
4. **P2** only if the card measures near 200 µA idle, and with `ring_max_io_ms` /
   `ring_io_errors` watched across a week. Note the 2026-08-08 snapshot already shows the FTL
   taking **553 ms for a single 4 KB write** with no errors at all — the card stalls on its own
   schedule, and a routine power-cycle adds a re-init to that on every silence→speech edge.
5. **P3** only as an explicit, user-visible capture tradeoff, behind a runtime toggle, never as
   a silent default.
